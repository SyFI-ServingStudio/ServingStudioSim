# Profile Add Python Kernel

Use this skill for Python-side L1 profiling additions. It covers runner/schema
registry work; it does not make a new kernel kind usable from Rust unless the
Rust timing kernel and bridge are also added.

## Ownership Rules

- Concrete `KernelArgs` subclasses live in `profiling/db/args.py`.
- `KernelKind` variants live in `profiling/db/kind.py`; add one only for a new
  kernel kind, not for a backend variant.
- Runner functions live in `profiling/runners/<family>/<backend>.py`.
- Registry rows live in `profiling/db/registry.py` as `KernelProfilerSpec`
  entries with lazy `RunnerRef` strings.
- Public `get_<kind>_times` / `count_missing_<kind>` functions are generated by
  `profiling/facade.py`; do not hand-write wrappers in `profiling/perf_api.py`.
- Existing-profiler runs should validate through `uv run python -m profiling`
  after the registry row lands; the CLI is a thin wrapper over those generated
  `perf_api` functions.
- Runner files allocate tensors, launch/profile kernels, and return
  `ComputeMetrics` or `CommMetrics`. They do not write SQL, edit DB rows,
  inspect JIT policy, choose subprocess envs, or mutate `CUDA_VISIBLE_DEVICES`.
- Use existing `Timer` methods, `Energy.perf(..., per_iter_time_ms=time_ms)` for
  compute energy, existing metric dataclasses, and existing env names whenever
  they fit. Ask before adding a new Timer method, metric family, cache variant,
  launcher protocol, or profiling environment.
- Most backends should use `default_env`; only use special env keys when the L1
  docs or user explicitly require them.

## Checklist Workflow

Copy this checklist into the working notes or plan before editing. Keep the
leading `[]` text, then mark each completed item as `[x]`.

- [] Read all required references and list the concrete doc anchors that justify
  the requested addition.
- [] Classify the request as one of: new backend for existing `KernelKind`, new
  Python runner for an existing table, or new `KernelKind`.
- [] If the request implies a new cache variant, Timer method, metric dataclass,
  launcher protocol, or subprocess env, stop and ask the user before editing.
- [] Choose names and confirm they are clear: `KernelKind` value, backend
  string, table stem, args dataclass name, runner function name, runner module,
  and generated perf API function names.
- [] Check that the runner kwargs, `KernelArgs` fields, DB args columns, and
  public dict spec keys will be identical and in the intended order.
- [] For a new `KernelKind`, add the enum variant to `profiling/db/kind.py`.
  For a new backend of an existing kind, leave `KernelKind` unchanged.
- [] Add or reuse the concrete `KernelArgs` dataclass in
  `profiling/db/args.py`; keep it frozen and field-only.
- [] Write or extend the runner file in `profiling/runners/<family>/<backend>.py`
  following the documented family/backend layout.
- [] In the runner, import optional heavy libraries lazily inside the profile
  function when possible, convert dtypes through the args contract, allocate
  inputs, call the selected `Timer`, call `Energy.perf` for compute rows, and
  return the correct metrics dataclass.
- [] For comm runners, use `MultiGpuLauncher` and a registry `gpu_count_fn`
  based on a clear spec field such as `num_gpus`.
- [] Add the `KernelProfilerSpec` row in `profiling/db/registry.py` with lazy
  `RunnerRef`, `args_schema`, `metric_family`, `batch_outlier_policy`,
  `subprocess_env`, optional `subprocess_module`, and optional `gpu_count_fn`.
- [] Ensure shared `table_name` rows have the same args schema and metric
  family; otherwise choose a separate table or ask about the design.
- [] Confirm no runner module is imported eagerly by the registry in the main
  process.
- [] Confirm no hand-written public wrappers were added to
  `profiling/perf_api.py`.
- [] Confirm `uv run python -m profiling list --json` shows the new table/backend
  and generated facade names.
- [] Add focused tests for dtype/spec coercion, registry wiring, lazy imports,
  facade generation, DB query/missing behavior, and any runner-specific
  validation that can run without a real GPU.
- [] Add a top-level CLI/perf API smoke path for the new profiler when a real
  GPU is available; use `uv run python -m profiling run ... --force` only for
  intentional refresh.
- [] Add agent-facing comments where they clarify ownership, extension rules,
  env decisions, or generated-facade behavior.
- [] Report to the user: doc anchors used, classification, files changed,
  public facade names, example input spec, validation results, real profile
  results or why no GPU run was possible, and remaining Rust-side work if any.

## Validation Checklist

Copy this validation checklist and mark items as `[x]` as they complete.

- [] `uv run ruff check` on every changed Python file.
- [] Focused pytest covering the new args/registry/facade/table behavior.
- [] Test that importing `profiling.db.registry` does not import the new runner
  module eagerly.
- [] Test that the generated `perf_api` function names exist, no manual wrapper
  was added, and `python -m profiling list --json` reports the new table/backend.
- [] Test `count_missing_<table>` is read-only and returns expected misses on a
  clean DB.
- [] Test `get_<table>_times(..., force=True)` or JIT-fill persists rows through
  the table path using a fake `GpuPool` when possible.
- [] For real CUDA validation, run through `uv run python -m profiling`, not the
  runner, and report specs, DB path, `time_ms`, `energy_j`, and missing count.
- [] For compute energy, verify the runner passes `per_iter_time_ms=time_ms` to
  `Energy.perf`.
- [] For comm profiles, verify `gpu_count_fn` and launcher behavior with the
  smallest safe GPU count.
- [] If a new `KernelKind` was added, explicitly state whether Rust
  `simulator/src/timing/kernels/*` and bridge wrappers are still pending.
- [] Re-read the changed files once for code order, variable names, and
  future-agent comments before final response.

## File Map

Common Python-side files:

- `profiling/db/kind.py`: `KernelKind` enum for new kernel kinds only.
- `profiling/db/args.py`: concrete `KernelArgs` dataclasses.
- `profiling/runners/<family>/<backend>.py`: profiling runner functions.
- `profiling/runners/metrics.py`: only for rare new metric dataclasses.
- `profiling/runners/comm/_launcher.py`: only for rare new launcher protocols.
- `profiling/profilers/timer.py`: only for rare new timing methods.
- `profiling/profilers/energy.py`: usually unchanged; runners pass measured
  `time_ms` into it.
- `profiling/exec/env.py`: only when a documented new subprocess env is needed.
- `profiling/db/registry.py`: `KernelProfilerSpec` row and imports for args.
- `profiling/facade.py`: normally unchanged; generated APIs come from registry.
- `profiling/perf_api.py`: normally unchanged; no manual wrappers.
- `profiling/cli.py`: normally unchanged; existing-profiler CLI is generated
  from registry table stems.
- `tests/`: focused unit tests and optional GPU smoke tests.

## Stop And Ask

Ask before editing when:

- No L1 doc contract supports the file location, API shape, name, or behavior.
- The kernel needs a new metric family, cache interpolation type, Timer method,
  launcher protocol, or subprocess environment.
- The requested backend needs a different args schema than existing backends
  that currently share a table.
- A real GPU run would write to the shared `profile.db` and the user has not
  explicitly approved updating it.
