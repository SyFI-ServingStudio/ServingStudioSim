# Profile Add Python Kernel

Use this skill for Python-side L1 profiling additions. It covers runner/schema
registry work; it does not make a new kernel kind usable from Rust unless the
Rust timing kernel and bridge are also added.

Python per-kernel knowledge is consolidated in **one file** per kind:
`profiling/kernels/<kind>.py`. That mirrors the Rust layout
`simulator/src/timing/kernels/<kind>.rs`. The runner stays separate because the
main process must not eager-import heavy libraries (torch, CUDA, vllm).

## Ownership Rules

- Per-kernel module `profiling/kernels/<kind>.py` owns the `KIND` constant, the
  concrete `<Kind>Args` dataclass, and the `register(KernelProfilerSpec(...))`
  side-effect call. All of this is one file per kind.
- Runner functions live in `profiling/runners/<family>/<backend>.py` and stay
  separate (architectural requirement: main process must not eager-import torch
  or any other env-specific heavy library). The per-kernel file refers to the
  runner only via `RunnerRef(module_name=..., function_name=...)`.
- `profiling/kernels/__init__.py` is the barrel that imports each per-kernel
  module so its `register(...)` side effect runs once. Adding a kind means
  adding one `from . import <kind>` line here.
- Public `get_<kind>_times` / `count_missing_<kind>` functions are generated by
  `profiling/facade.py` from the registry; do not hand-write wrappers in
  `profiling/perf_api.py`.
- Runner files allocate tensors, launch/profile kernels, and return
  `ComputeMetrics` or `CommMetrics`. They do not write SQL, edit DB rows,
  inspect JIT policy, choose subprocess envs, or mutate `CUDA_VISIBLE_DEVICES`.
- Use existing `Timer` methods, `Energy.perf(..., per_iter_time_ms=time_ms)` for
  compute energy, existing metric dataclasses, and existing env names whenever
  they fit. Ask before adding a new Timer method, metric family, cache variant,
  launcher protocol, or profiling environment.
- Most backends should use `default_env`; only use special env keys when the L1
  docs or user explicitly require them.

## Checklist Workflow

Copy this checklist into the working notes or plan before editing. Keep the
leading `[]` text, then mark each completed item as `[x]`.

- [] Read all required references and list the concrete doc anchors that justify
  the requested addition. Open `profiling/kernels/single_gemm.py` as the
  shape-of-truth example.
- [] Classify the request as one of: **new backend for an existing
  `KernelKind`**, new Python runner for an existing table, or **new
  `KernelKind`**. The two cases take *different* file paths below — pick
  before editing. If the request implies a new cache variant, Timer method,
  metric dataclass, launcher protocol, or subprocess env, stop and ask the
  user before editing.
- [] Choose names and confirm they are clear: `KIND` wire string (only for a
  new kind), backend string, args dataclass name (only for a new kind),
  runner function name, runner module, and generated perf API function names
  (`get_{kind}_times`, `count_missing_{kind}`). For a new kind, the `KIND`
  string is the single source of truth — it doubles as the table stem and
  the facade stem; do not hand-type it twice.
- [] Write or extend the runner file
  `profiling/runners/<family>/<backend>.py`. Import optional heavy libraries
  lazily inside the profile function, convert dtypes through the args
  contract, allocate inputs, call the selected `Timer`, call `Energy.perf` for
  compute rows, and return the correct metrics dataclass. For comm runners use
  `MultiGpuLauncher` and supply a `gpu_count_fn` via the registry row.
- [] **New `KernelKind`:** create `profiling/kernels/<kind>.py`. Define `KIND`
  as a string constant, define `<Kind>Args(KernelArgs)` as a frozen dataclass,
  and call `register(KernelProfilerSpec(kernel_kind=KIND, backend=..., ...))`
  with a lazy `RunnerRef`. Use `table_name=KIND` unless an explicit doc
  contract says otherwise. Mirror `profiling/kernels/single_gemm.py`. Then
  add `from . import <kind>` to `profiling/kernels/__init__.py` so the
  side-effect register call runs.
- [] **New backend for an existing `KernelKind`:** open the existing
  `profiling/kernels/<kind>.py` and add another
  `register(KernelProfilerSpec(kernel_kind=KIND, backend="<new>", ...))`
  call. Reuse the existing `<Kind>Args` schema and `table_name=KIND`. Do
  NOT create a second per-kernel file and do NOT add a new barrel line.
  The registry validator rejects same-table-different-kind, and the facade
  builder rejects two stems on the same kind — so a second file would
  immediately fail at first registry access.
- [] Confirm `uv run python -m profiling list --json` shows the new
  table/backend and generated facade names.
- [] Add focused tests covering dtype/spec coercion, registry wiring, lazy
  imports, facade generation, and DB query/missing behavior. Add a real-GPU
  smoke through `uv run python -m profiling run ... --force` if hardware is
  available.
- [] Report to the user: doc anchors used, classification, files changed
  (per-kernel module path + runner module path + barrel line), public facade
  names, example input spec, validation results, real profile results or why
  no GPU run was possible, and remaining Rust-side work if any.

## Validation Checklist

Copy this validation checklist and mark items as `[x]` as they complete.

- [] `uv run --with ruff ruff check profiling/ tests/` clean.
- [] Focused pytest covering the new args/registry/facade/table behavior.
- [] Test that importing `profiling.db.registry` or any per-kernel module does
  not eagerly import the runner module (verify via
  `sys.modules` inspection — the runner module name must NOT appear after a
  bare `import profiling.kernels.<kind>` but `RunnerRef` must resolve when
  asked).
- [] Test that the generated `perf_api` function names exist, no manual
  wrapper was added, and `python -m profiling list --json` reports the new
  `(table, backend)`.
- [] Test `count_missing_<table>` is read-only and returns expected misses on a
  clean DB.
- [] Test `get_<table>_times(..., force=True)` or JIT-fill persists rows
  through the table path using a fake `GpuPool` when possible.
- [] For real CUDA validation, run through `uv run python -m profiling`, not
  the runner directly, and report specs, DB path, `time_ms`, `energy_j`, and
  missing count.
- [] For compute energy, verify the runner passes `per_iter_time_ms=time_ms`
  to `Energy.perf`.
- [] For comm profiles, verify `gpu_count_fn` and launcher behavior with the
  smallest safe GPU count.
- [] If a new `KernelKind` was added, explicitly state whether Rust
  `simulator/src/timing/kernels/*` and bridge wrappers are still pending.

## File Map

Per-kernel touch points (these are the files you add or edit per new kind):

- `profiling/kernels/<kind>.py` — KIND constant + `<Kind>Args` dataclass +
  `register(KernelProfilerSpec(...))`. **One file per kernel kind.**
- `profiling/runners/<family>/<backend>.py` — runner function. Stays separate
  due to lazy-import constraint.
- `profiling/kernels/__init__.py` — barrel; add one `from . import <kind>`.

Framework files (normally unchanged when adding a kernel):

- `profiling/db/kind.py` — `KernelKind = str` type alias.
- `profiling/db/args.py` — `KernelArgs` base + `DType`. Concrete subclasses now
  live next to their kind under `profiling/kernels/`.
- `profiling/db/registry.py` — `KernelProfilerSpec`, `RunnerRef`,
  `MetricFamily`, `register()`, `_ensure_loaded()`. Do not append rows here;
  call `register(...)` from the per-kernel module instead.
- `profiling/db/__init__.py` — re-exports of registry/args types. Per-kernel
  `<Kind>Args` is imported from `profiling.kernels.<kind>` by callers, not
  re-exported here.
- `profiling/facade.py`, `profiling/perf_api.py`, `profiling/cli.py` — drive
  off the registry; no manual wrappers.
- `profiling/runners/metrics.py`, `profiling/runners/comm/_launcher.py`,
  `profiling/profilers/{timer,energy}.py`, `profiling/exec/env.py` — only
  touch when a new metric family / launcher protocol / Timer method /
  subprocess env is genuinely required (ask first).
- `tests/` — focused unit tests and optional GPU smoke tests.

## Stop And Ask

Ask before editing when:

- No L1 doc contract supports the file location, API shape, name, or behavior.
- The kernel needs a new metric family, cache interpolation type, Timer
  method, launcher protocol, or subprocess environment.
- A real GPU run would write to the shared `profile.db` and the user has not
  explicitly approved updating it.
