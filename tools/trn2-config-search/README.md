# trn2-config-search

Searches serving configurations of Qwen3.8-Flash-Next BF16 on one trn2.48xlarge
(`qwen4_exp_neuron_bf16[_speculative]`, `doc/pr/trn2-flashnext/`) with the simulator
only. It never profiles and never touches a Neuron device: every launch is
`--no-gpu`, and configs whose rows are missing are reported as `needs_profiling`.
Results and the current conclusions: `doc/pr/trn2-flashnext/CONFIG_SEARCH.md`.

## Pipeline

One **stage file** (`stages/*.yaml`) describes a set of configs and workloads. One
**experiment directory** `EXP` (by convention `logs/trn2/search/<stage>`) holds
everything a stage produces.

```bash
source ../neuron_env.sh; export PATH=$HOME/.cargo/bin:$PATH SERVINGSTUDIO_NO_GPU=1
S="uv run --no-sync python tools/trn2-config-search/search.py"
$S plan  tools/trn2-config-search/stages/s1_layout.yaml logs/trn2/search/s1_layout
$S probe logs/trn2/search/s1_layout -v          # ok / invalid / needs_profiling per config
$S run   logs/trn2/search/s1_layout --parallelism 48
$S collect logs/trn2/search/s1_layout [--slo chat=2000,100]
$S report  logs/trn2/search/s1_layout [more EXPs ...] --out report.md
$S top     logs/trn2/search/s1_layout stages/next_seeds.yaml --n 2 --metric total_tok_s
```

| Step | What it does | Writes |
|---|---|---|
| `plan` | expands the stage into configs (`trn2_search/space.py`), writes the traces | `stage.yaml`, `configs.jsonl`, `traces/` |
| `probe` | renders each config as a one-run preset, expands it with the launcher's own `expand_preset`, and runs the simulator's `dry-run` (the arch build: layout checks, HBM check, every profile.db lookup). Resumes by label | `probe.jsonl`, `probe/<label>/` |
| `run` | groups the `ok` configs by knob set into launcher presets (`compound` groups `config` x `workload`) and runs them all in one launcher batch with `--no-gpu --no-plot`. The launcher resumes finished runs | `presets/`, `runs/<preset>/<label>/<workload>/` |
| `collect` | one row per finished run: throughput, TTFT/TPOT percentiles, goodput per SLO, the R0-R7 cluster ladder | `results.jsonl`, `results.csv` |
| `report` | Pareto frontiers (tok/s vs TPOT p50 and vs TTFT p90), best config per objective, knob sensitivity, what-if rank agreement, ladders of the top configs | `report.md` |
| `top` | the best configs per workload as `seeds` for the next stage | a seeds YAML |

`probe` exists because the launcher aborts a whole sweep when one cache key fails
its prebuild, and under `--no-gpu` a missing row is such a failure.

## Stage files

```yaml
name: s2_knobs
family: unified            # unified | mtp | pd
workloads_file: tools/trn2-config-search/stages/workloads.yaml
workloads: [fixed_2k_512, chat_r1]   # default: every workload in the file
accept_rates: [0.5, 0.71]  # mtp only: one trace per workload and rate
base: {layout: dp4-tp8-g8-ep32-mt1, max_batch_tokens: 2048}
layouts: auto              # or a list; auto enumerates layout_ranks (default [32, 64])
grid: {tp_collective: [all_reduce, reduce_scatter_all_gather]}   # crossed
oat: {max_batch_tokens: [1024, 4096]}  # each varied alone from every point
seeds_file: tools/trn2-config-search/stages/s1_top.yaml          # replaces the bare base
scenarios:                 # what-if overrides applied to every config
  base: {}
  host_half: {host_time_scale: 0.5}
  no_pad: {spmd_padding: false}
  moe_prefill_3x: {kind_time_scale: ["moe_block@256=0.3333", "moe_routed_experts@256=0.3333"]}
```

Knobs are the arch and worker parameter names (`list-params`, and the knob table in
`doc/pr/trn2-flashnext/README.md`), plus:

- `layout`: `dp<attn_dp>-tp<attn_tp>-g<gdn_tp>-ep<moe_ep>-mt<moe_tp>`;
- `replicas`: defaults to as many replicas as fit the 64 cores;
- unified / MTP workers default to the flashnext scheduler:
  `max_prefill_chunks_per_partition: 1` and (unified) `dp_placement: vllm-least-loaded`;
- P/D: prefix with `prefill.` / `decode.`. A scenario's unprefixed knobs apply to both
  pools.

A config's `label` is `<family>_<layout>_<hash>` of its knobs and scenario; `core_id`
hashes the knobs before the scenario, so a config and its what-if variants share it.

## Workloads

`stages/workloads.yaml`, generated by `trn2_search/workloads.py` (seeded; the same spec
writes the same bytes). Kinds: `file` (an existing trace), `fixed`, `chat` (uniform
lengths, Poisson arrivals at `rate` req/s) and `agentic` (bursts of Poisson(`burst_mean`)
requests at `burst_rate` bursts/s, each within `burst_spread_ms`). Presets set
`request_rate: 1.0`: under `trace_timed` the simulator divides trace arrival times by
`request_rate`, whose default is 10.

## Metrics

- `total_tok_s` is prefill + decode tokens over the simulated span; `tok_s_per_chip`
  divides by 16 chips for every config here.
- TTFT and TPOT percentiles are over completed requests (TPOT = each request's mean
  inter-token time).
- `goodput_req_s@<slo>`: completed requests meeting TTFT <= t and TPOT <= p, per second
  of span. Default SLOs are in `search.py` (`DEFAULT_SLOS`); `collect --slo name=t,p`
  adds or replaces one. Re-run `collect` to change SLOs; nothing re-simulates.
- `gap_*`: the analyzer's cluster buckets (`reports/optimality_report.json`) as fractions
  of R0 GPU-time. `report` groups them as idle/imbalance, launch+batching (R2-R3),
  communication, kernel gap, hardware gap, excess over necessary work.
