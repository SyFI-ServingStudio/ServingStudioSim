GLM-5.2 前缀分级存储：DP8 与 PP8

8 张 B200 跑 TraceLab monotonic 闭环 agent 会话（每轮平均 166k 上下文，新算约 1.7k token），前缀放在 HBM、DRAM、SSD 三级。对比 DP8EP8 和 PP8，看峰值吞吐、DRAM 需要多大、HBM 够不够，以及每 1M token 的成本。

模型GLM-5.2 NVFP4 · 78 层全 DSA GPU8 × B200 · $6.5/h DRAM50 GB/s/GPU SSD8 TB · 10 GB/s/GPU 窗口8 h 仿真，取 2–7 h 稳态 调度SPF · SRPT · load budget · 读等待 1 s

结论

41–42r/s · PP8 + 750 GB

PP8 配 750 GB DRAM 是最好的配置。峰值是 DP8 同 DRAM 时（28.9）的 1.45 倍，c1000 时 p90 TTFT 1.7 s，DP8 是 21 s。

750 GBDRAM / GPU

DRAM 要大到装下活跃会话的工作集。150 GB 时两种部署都被 SSD 10 GB/s 卡住（DP8 21.3、PP8 26.5 r/s）。750 GB 时 DP8 已经与 DRAM 无限相同（28.9 对 29.3）。

0.70DP rank 均衡度

DP8 的上限来自 rank 失衡。EP 要求 8 个 rank 每步同步，每步都要等最忙的 rank。放宽 load budget 反而更慢（不限额度时 18.0 r/s），因为失衡更严重。

4–15%DP8 HBM 占满时间

DP8 会撞上 HBM 下限，PP8 不会。DP8 每个 rank 只有 128 万 token 的 KV，从 c750 起就有 4–15% 的时间被进行中的请求占满。PP8 共用 1410 万 token 的池子，最高只用到 89%。

c1125PP8 崩溃点

PP8 过了峰值会崩，原因是缓存被挤掉，HBM 并没有满。等读的请求占住 HBM，缓存的旧前缀从 71% 降到 33%，HBM 命中从 19% 降到约 1%，更多请求要去 DRAM 读。部署时要把并发限制在约 c1000。

$0.20/1M 新 token · PP8

自建成本比在线厂商低 18–82 倍。DP8 是 $0.28。同样的流量按厂商的「新 token + cache read」价计费，94–99% 的账单是 cache read，因为每轮有 148k 缓存 token、只新算 1.76k。

2 · TTFT 与吞吐的权衡

每个点是一个并发，按并发从小到大连线。越靠右下越好：吞吐高，TTFT 短。线往左上折回，说明过了峰值、系统开始崩：吞吐下降，TTFT 继续上升。

表中只取实际跑过的并发点，没有插值。在 p90 ≤ 2 s 的要求下，PP8 + 750 GB 的吞吐大约是 DP8 的 2 倍。DP8 c500 到 c750 之间没有测点，所以它满足 2 s 的真实上限在 19–28 之间。

4 · DP8 的上限：rank 失衡

load budget 让每个 DP rank 每步最多处理 4096 个新 token（每个 rank 单独计算额度）。把额度放大后，单个 rank 的效率确实变高，但每个 rank 手上平均只有 1–2 个请求。一旦某个 rank 拿到大 chunk（比如新会话第一轮约 28k token），其余 7 个 rank 这一步就基本闲着。

5 · HBM 够不够

不能被挤掉的 KV 包括两部分：正在算的请求，和正在从 tier 读的请求。按 vLLM 的做法，开始读之前就要分配好整个请求的 KV 空间，一直占到读完、被调度为止。表中是这部分占 KV 池的比例（750 GB DRAM，2–7 h）。

  • DP8：每个 rank 的 KV 约 128 万 token，只放得下 7–8 个 166k 的请求。HBM 占满时新的读开始不了，调度就停住。c1000 时每卡 70.6 GB 的分布是：正在算 14.1 GB，等读 31.1 GB，旧前缀 21.8 GB，空闲 3.5 GB。
  • PP8：过峰后旧前缀被等读的请求挤掉，HBM 命中跌到约 1%，GPU 利用率从 0.85 降到 0.55，形成恶性循环。不可挤占的部分从来没有接近满。
  • 两种部署都一样：等读的部分比正在算的部分大。读完立刻调度、边读边算，或者给旧前缀留一个最低配额，都可能改善。这些改进都还没有仿真过。

8 · 单次 burst：100k 前缀 + 8192 新 token

128 个请求在 t=0 同时到达，每个请求的 100k 前缀已经在 KV 里，只需新算 8,192 个 token、输出 1 个。每个 rank 的 chunk 是 8192。吞吐只算新 token。

注意事项

  • 闭环 run 用的都是 pp-study 的自定义调度，不是原版 vLLM 调度。包括：SPF（新 prefill 短的先算）、SRPT、load budget（每 rank 4096，backlog 1M–3M）、tier 读最多等 1 s（等不到就先跳过）、60 s 强制调度、warm start、会话粘在同一 rank。PP8 另外有 tier 读在 stage 间均摊和 even microbatch 切分。单次 burst（第 8 节）用的是默认的 chunked prefill，没有这些策略。
  • PP8 和 DP8 的专家路由不完全一致。DP8 用 vLLM c32_long 的实测分布。PP8 是 EP1，用这个分布会缺 66 行 MoE profile 数据，所以改用 SGLang TP4 的实测分布。两者的 MoE 时间会略有出入；补齐数据需要上 GPU。
  • KV 预算是推算值，没有实测。DP8 每卡 70.56 GB 取自 public preset；PP8 每卡 100.08 GB 按同一规则推出。
  • 每个点只跑了一个 seed，没有做方差。
  • decode 不在这几张卡上（external decode），只体现为每轮之间的 tool wait 时间。
  • 代码改动还没提交。改动让全注意力架构（如 GLM-5.2）也能用分级前缀存储，共 7 个文件。不开 tier 时结果与改动前逐位一致；just test-cpu：Rust 1383 个全部通过，pytest 4081 个通过，另有 14 个 error，原因是这个 worktree 没有初始化 vllm 子模块。
