# Qwen3.8-27B-NVFP4 evidence (B200, vLLM TP1)

This is review evidence for the `qwen35_vllm_nvfp4_gdn_dense` arch on `nvidia/Qwen3.8-27B-NVFP4`. It covers:
- what the simulator models;
- how it was checked against vLLM captures;
- what is still open.

It is not an accepted baseline. Tolerance failures and the known gaps below stay explicit, and no golden has
been recorded.

## Deployment modeled

vLLM V1 on one B200, from the vLLM fork `servingstudio-alignment` at `892da082` (*catalog*):

- `--language-model-only`, `--max-model-len 131072`, prefix caching on.
- `--kv-cache-dtype fp8_e4m3` and `--mamba-ssm-cache-dtype float32`.
- `--gpu-memory-utilization 0.85`.
- `max_num_seqs` left at vLLM's default (1024). No case reaches it; the highest concurrency is c256.
- FULL_AND_PIECEWISE CUDA graphs.
  - `max_cudagraph_capture_size` equals the chunk size: 2048, 4096 or 8192.
  - The capture list is vLLM's own list for that cap: 147, 275 or 531 sizes.
- One API server.
- Warm JIT and autotune caches. A pass that logged "No tuned config" or a smaller KV pool was discarded and
  rerun.

KV pool per chunk size, from `Available KV cache memory` in the warm workload passes (*measured*):

| Chunk | KV pool | Jobs |
|---:|---:|---|
| 2048 | 125.52 GiB | 6479 and every warm chunk-2048 pass |
| 4096 | 123.75 GiB | 6566, 6574 |
| 8192 | 119.82 GiB | 6570, 6572 |

A larger capture cap captures more graphs, so the pool shrinks with the chunk size.

## How each model feature is modeled

- **Precision is read from the config.** `qwen35_model_cfg` reads ModelOpt `MIXED_PRECISION`
  `quantized_layers`, and maps the shard names onto vLLM's fused modules
  (`packed_modules_mapping`, `qwen3_5.py`):
  - GDN `in_proj_qkvz` and `out_proj`, GQA `qkv_proj` and `o_proj` run FP8 per-tensor through FlashInfer
    `bmm_fp8`.
  - The MLP `gate_up` and `down`, and the lm_head, run NVFP4 through FlashInfer's CuTeDSL block-scaled GEMM,
    after a separate `scaled_fp4_quant`.
  - `in_proj_ba` stays BF16 (`F.linear`).
  - Any other mix fails to fit. The arch has no `fp8` flag.
- **Producers write the GEMM inputs.** The FP8 activation of every FP8 linear comes from the Inductor-fused
  norm or static-quant kernel in front of it, so the GEMM leaf carries no quant.
- **Norms.** `multi_add_rms_norm` has five variants, all profiled as Inductor emits them:
  - the first layer's norm, which has no residual add;
  - the GDN input norm;
  - the GQA input norm;
  - the post-attention norm;
  - the final norm.
- **Gated DeltaNet** (`vllm_qwen35_gdn_local`) carries every launch the capture shows:
  - the `in_proj_ba` contiguous copy, the decode q/k/v rearrange, and the core-output zero, strided copy and
    cat;
  - the state gather, zero and scatter (`indexed_row_copy`);
  - the varlen causal conv and the chunked delta rule (FlashInfer on SM100);
  - the gated RMSNorm and the output quant.

  The decode path depends on the step:
  - A decode-only step runs the packed recurrent decode.
  - A mixed step's decode rows run the sigmoid-gating recurrent decode, and join the prefill's varlen conv
    as length-1 rows (`GdnPrefillOp::decode_rows`).
- **Gated GQA** (`vllm_qwen35_gated_gqa_local`):
  - the fused QK norm + RoPE + gate kernel and the query and gate quant;
  - the KV append into the FP8 cache at the real tokens;
  - FlashInfer trtllm-gen FMHA over the FP8 KV, with separate context and decode launches in a mixed step.

  FA4 does not run here: vLLM falls back because FA4 does not take head dim 256 with an FP8 KV cache.
- **Dense MLP** (`vllm_nvfp4_swiglu_mlp_local`): NVFP4 quant, then `gate_up`, then Inductor `silu_and_mul`,
  then NVFP4 quant, then `down`.
- **CUDA graphs.**
  - A step of at most the largest capture size pads to the next captured size, and the compiled pieces run at
    the padded rows.
  - A PIECEWISE replay runs the GDN core and attention eagerly at the real tokens.
  - A FULL-graph (uniform decode) replay runs the GDN decode conv and recurrent kernels over the padded rows.
    Each padded row carries `PAD_SLOT_ID` and returns before touching state, so those two kernels are priced
    at the real rows.

### KV accounting

vLLM's hybrid allocator sizes the attention block so that one attention page holds one GDN state page:
- The block is 1568 tokens (*catalog*: "Setting attention block size to 1568 tokens").
- There are 4 KV groups of 16 layers, each with 3 GDN layers and 1 attention layer. A block is 51,380,224 B.
- A request holds ceil(T / 1568) attention blocks plus 6 GDN state blocks (2 copies × 3).

`kv_layout::hybrid_attention_state_layout` derives this from the config. At 134.7761 GB (125.52 GiB) the
simulator reports 29.13x concurrency at 131072 tokens (*simulated*); vLLM logs 29.14x (*measured*).

## Campaign: 20 operating points (TP1)

The pack derives every case from the corpus and the measured pools in `make_pack.py`:
- cases 01-15 at chunk 2048, with pools pinned for 14 (1786 blocks) and 15 (1118 blocks);
- cases 16-20 at chunk 4096 and 8192: the prefill spectrum, the IO quadrants and full saturation.

Case 09's rate is 0.8 × the knee measured in case 10.

The matrix is [`alignment_matrix.md`](alignment_matrix.md). Every case runs at the single multiplier 1.0483.
The causes of the misses:

- **Server TTFT low, cases 03-05, 07 and 09.** These run -10.6% to -19.4%. A prefill-carrying PIECEWISE step
  has a 7-43 ms additive host gap (*measured*, nsys `gpu_cycle` minus kernel busy). A pure-decode FULL-graph
  step has 0.3-0.7 ms. The single multiplier spreads that gap over all steps, so TTFT reads low; vLLM's
  frontend queueing adds to it.
- **TPOT and E2E high, cases 11-13.**
  - In c1 decode (case 12) the workload pass's decode cycle median is 6.04 ms, while the nsys pass's kernel
    busy is 6.25 ms. nsys stretches these kernels by about 3.5%.
  - The simulator aligns to the nsys kernels (+1.6%), and the multiplier then adds 4.8% to FULL-graph steps
    that have no host gap.
- **Iteration population, cases 01, 02, 04, 09, 15, 16 and 17.** The counts are off by 1.2-2.6% against
  1%. Closed-loop requests re-enter a few steps late through the client and frontend round trip. E2E in these
  cases stays within -7.2% to +3.1%.
- **Case 05 kernel -5.55%** (the decode-heavy cases read -2% to -4%). Small-M decode GEMMs run slower in
  serving than the profiled rows: measured over profiled is 0.79-0.91 for `gate_up`, `out_proj`, `qkv_proj`,
  `qkvz` and `down`.
  - In serving, `gate_up` grows from 19.1 to 22.4 µs over M 4-64. The rows stay at 17.6-17.9 µs.
  - Serving takes its runner from the capture's autotune cache: nvjet at B <= 16, CUTLASS at 17-64. The
    profiler re-tunes in its own process.
  - L2 flush is ruled out: the rows flush 2× L2 and are freshly measured.
- **Case 01 server TTFT +26.9%.** This is on a clean recapture (frontend prep mean 4.4 ms), and its structural
  counts differ by 2.3%. The cause has not been found.

The nsys passes of cases 10, 16-20 show one 7-13 s inter-iteration stall at a fixed step. It reproduces
across jobs, so it is an nsys flush. It is excluded from duty-cycle readings, and E2E comes from the workload
passes.

## Changes that reach other models

- **GDN causal-conv rows** (`gdn_causal_conv_{prefill,decode}`, B200). 459 rows were re-measured with vLLM
  892da082's state-first conv-state layout. GLM-5.3-Flash members move by -0.9% to +0.5%. The H200 rows that
  Qwen3.6 reads are unchanged.
- **`kv_layout` helpers.** Qwen3.6 and GLM-5.3-Flash now call the shared hybrid block and state-layout
  helpers. The formula is the same:
  - Qwen3.6 timing-predict is bit-identical;
  - the GLM-5.3-Flash tests pass unchanged.
- **`GdnPrefillOp::decode_rows`.** Existing callers pass 0, so their cost is unchanged.
- **`gdn_gated_rms_norm` grid** extends from 2^18 to 2^19 rows. Existing members read no new rows.
- **`single_gemm` m axis.** Only a backend list of exactly `flashinfer_fp8_tensor` gets the denser axis. The
  MXFP8 axis and every other backend keep theirs.
- **`flashinfer_attn_{prefill,decode,rect}` no longer list `trt`.** No row was ever measured for it, and no
  arch selected it.
- **model.work.**
  - The Qwen3.5 dense builder now counts its RMSNorm weights. This adds 668,672 parameters to the Qwen3.6
    golden, which now matches the checkpoint's safetensors header. No simulator prediction moves.
  - `_with_fp8_kv_cache` generalizes the earlier MLA-only override. The three GLM-5.3 FP8 archs are
    unchanged.
- **Launcher.**
  - A pack may declare one top-level `gpu_time_multiplier`; it defaults to 1.0, so existing packs render
    unchanged.
  - `record_extraction` rejoins a split structured record. Records that were not split parse as before.

## Modeling choices

- **One multiplier from `diverse_100`** for every deployment and case. There is no per-step host model.
- **Real decode rows in a FULL-graph GDN decode**, because padded rows exit on `PAD_SLOT_ID`. The copies and
  compiled pieces stay at the padded rows.
- **The KV append uses the kernel page of 16 tokens**, not the 1568-token allocator block.
- **The arch refuses `num_layers` / `sim_num_layers` overrides.** The layer schedule comes from
  `layer_types`.
- **The first GDN layer is its own group**, because its input norm has no residual add. The location map
  places all 48 GDN layers' necessary work on the 47-layer group; run-level R6/R7 is unaffected.

## Known gaps and follow-up

- **The capture setup differs from the current `operate-run-alignment` rules.**
  - The captures used one API server, where the skill now asks for 4.
  - The chunk-8192 cases used vLLM's default 531-graph list, where the skill now asks for every 128 above
    2048.

  A recapture under the new rules would change TTFT in the high-concurrency cases and the chunk-8192 pool.
- **Small-M GEMM tactic mismatch** between the profiler and serving (case 05, decode GEMMs). This is a
  profiler-method question for every model and needs its own change.
- **`gqa.decode_attention`** reads +12.8% on `diverse_100` and -7% on case 05.
  - The canonical-batch projection overestimates length-scattered batches by 3.5-6%. This is a documented
    property of the 3-D grid.
  - Probe 6562 rules out max sequence length and page order (≤ 2%).
  - About 7% is unexplained.
- **Small in-graph decode kernels read +30% to +57%**: quant, gated norm, SiLU, zero and the strided copy.
  The rows are timed outside a graph.
- **`gdn.input_norm` reads -11% to -23%**, with a different ratio per case for the same Inductor kernel. The
  cause is unknown.
- **Not investigated:**
  - `gqa.prefill_attention` -5% at long prefixes;
  - `gdn.prefill.chunk_delta_rule` -7%;
  - prefill causal conv +16%;
  - mixed-step NVFP4 `gate_up` +7%.
- **About 1% of measured time is unmapped:** mamba precopy and postprocess, sampling, preprocess, and the
  FMHA fill memset.
- **R5 against model.work at the GEMM slots.** R5 picks compute or memory per slot, while model.work takes the
  per-iteration max. This is an Analyzer method question.
- **Not modeled:** sampling, MTP, vision.

## Reproduce

From the repository root. Set `PACK=presets/alignment/qwen38_27b_nvfp4_b200_tp1` and point `OUT` at a fresh
experiment directory:

```bash
uv run python -m launcher alignment-campaign check --pack "$PACK"
uv run python -m launcher alignment-campaign render --pack "$PACK" --host <host> --out-root "$OUT"
for phase in profile_workload profile_nsys timing_predict; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign label --pack "$PACK" --out-root "$OUT"
for phase in analysis_kernel simulation analysis_e2e; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign extract --pack "$PACK" --runs "$OUT" --out metrics.json
uv run python -m launcher alignment-campaign compare --pack "$PACK" --measured metrics.json --markdown
```

Host requirements:
- The profile phases need one B200 per pass.
- Each Slurm job needs its own port and scratch, with starts staggered by about 90 s.
- Warm the JIT and autotune caches with one pass per chunk size before the others start.
- vLLM's ZMQ IPC path (`TMPDIR` plus a uuid) must fit 107 bytes.

The public presets are checked by building every member against the committed profile.db, with no GPU:

```bash
just test-presets
```
