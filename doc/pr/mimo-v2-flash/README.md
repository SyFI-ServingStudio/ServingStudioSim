# MiMo-V2.6-Flash-RL evidence (B200, vLLM TP4/EP4)

This is review evidence for the `mimo_v2_vllm_fp8_swa_moe` arch on MiMo-V2.6-Flash-RL. It covers what the
simulator models, how it was checked against vLLM captures, and what is still open. It is not an accepted
baseline: tolerance failures and the known gaps below stay explicit, and no golden has been recorded.

## Deployment modeled

vLLM V1 on B200, from the vLLM fork `servingstudio-alignment` at `892da082`:
- **Parallelism.** Attention is TP4. The routed experts are EP4 over the same ranks
  (`--enable-expert-parallel`, linear placement, EPLB off, all-gather / reduce-scatter all2all).
- **Server args.** `--max-model-len 131072`, chunked prefill at 2048 tokens, `--max-num-seqs 100`,
  `--gpu-memory-utilization 0.85`.
- **Backends.** BF16 KV with `--block-size 16`, the `flashinfer_trtllm` MoE backend and `FLASH_ATTN_DIFFKV`
  attention.
- **Off.** MTP, vision and audio.

| Workload | Captures |
|---|---|
| `trace/diverse_100.csv`, trace-timed, c100, default graph sizes 1..200 | nsys pass job 6264 (5026 iterations); workload pass job 4223 (100/100 requests); token corpus at HF `18506fd7` |
| The 15 cases of `mimo_v26_flash_b200_tp4` | Warmed nsys and workload passes per case. Graphs are captured to 2048 tokens (`max_cudagraph_capture_size` 2048). Cases 14 and 15 pin the KV pool with `--kv-cache-memory-bytes`. |

## How each model feature is modeled

| Feature | vLLM | Simulator |
|---|---|---|
| Global and sliding-window attention | FA4 varlen (`flash_attn_diffkv.py`). K and V are packed into one paged cache. The window start rounds down to a 128-key tile. The split count comes from `FlashPrepareScheduler`. | `fa4_varlen_attention` / `vllm_fa4`, with one config per layer kind. Steps are projected onto (decode requests, prefill tokens, equivalent context) in CTA waves, and a window is charged as window + 127 keys. |
| QKV | Per-token FP8 activation quant, then the FP8 block-scaled GEMM | `elementwise` quant plus `single_gemm` FP8 block-scale |
| RoPE and KV insert | Partial RoPE with V scale; `triton_reshape_and_cache_flash_diffkv` writes K\|V | `elementwise` + `kv_cache_append` / `vllm_triton_diffkv` (K192 / V128) |
| o_proj, router, lm_head | BF16 cuBLAS | `single_gemm` / `torch_linear_vllm`; the router returns FP32 logits |
| Routed experts | `TrtLlmMxfp4ExpertsMonolithic` under `FLASHINFER_TRTLLM_MXFP4_BF16`: no activation quant, routing inside the call | `nvfp4_fused_moe` / `flashinfer_trtllm_sm100_mxfp4_bf16` through `Nvfp4MoeLocalWorklet` with `activation_format` bf16. It is a `Max` over the four EP ranks' corpus-routed workloads. |
| Collectives | `allreduce_rms` fuses every TP all-reduce with the residual add and the next RMSNorm (MNNVL), 2 per layer plus the embedding's | `all_reduce_residual_rms_norm` / `flashinfer_mnnvl`. A step above the fused cap (4096 tokens at TP4) is refused; it never occurs at chunk 2048. |
| CUDA graphs | FULL_AND_PIECEWISE. FULL decode keys exist only for capture sizes up to `max_num_seqs` (`cudagraph_dispatcher.py:216-235`); other steps replay PIECEWISE or run eager. | Tokens pad to the capture sizes. A uniform decode within `full_decode_graph_max_tokens` prices attention at the padded request count, and FA4's `full_cudagraph_max_size` follows it. |
| Head | Last-row select, lm_head, logits all-gather | `elementwise`, `single_gemm`, and the all-reduce curve standing in for the all-gather |

Sampling, MTP, vision and audio are not modeled.

### KV accounting

The arch declares two KV parts, as vLLM's hybrid allocator holds them:
- global layers per token;
- sliding-window layers at their window, padded to vLLM's whole groups (39 layers make 5 groups of 9, so 45
  slots).

At the capture's logged 110.52 GiB, `--kv-report` gives 118.88x concurrency at 131072 tokens per request.
vLLM logged 118.76x (+0.10%). `attn_gpu_memory_gb` is the capture's logged per-GPU pool × 1.073741824
(*measured*):

| Public sim preset; `diverse_100` Check 1 (job 6264) | 110.07 GiB | 118.1868 |
| `diverse_100` simulation (workload pass, job 4223) | 110.6 GiB | 118.7558 |
| Campaign, graph-2048 config | 108.44 GiB | per case, in the pack |

## Check 1: kernel alignment on `diverse_100`

This is the duration-weighted signed error of the simulated critical path against the measured one, per
iteration (*simulated* vs *measured*). Source: `logs/20261012_6_mimo_diverse100_final/check1_derived.md`.

| stage | n | measured ms/iter (mean) | simulated ms/iter (mean) | signed rel. err median |
|---|---|---|---|---|
| decode | 4549 | 6.712 | 7.127 | +6.18% |
| mixed | 477 | 39.517 | 39.404 | -0.17% |
| all | 5026 | 9.825 | 10.190 | +5.93% |

Mapping covers 99.26% of the measured critical path. The unmapped part is preprocess, sampling and the
embedding's `zeros_like`. The recommended `gpu_time_multiplier` is 1.1103.

The decode gap is +0.415 ms/iter. Its largest items, per operation (section B of the same file):

| op | decode meas ms/iter | decode sim ms/iter | rel | cause |
|---|---:|---:|---:|---|
| `moe.routed` | 2.891 | 3.233 | +11.8% | The FULL graph's padded rows are charged as corpus-sampled tokens; see the note below the table. |
| `moe.router` | 0.202 | 0.345 | +70.4% | The row is the eager sum of the split-K GEMM and its reduce. In the graph they overlap under PDL: 4.2 µs on path against 7.3 µs in the row. |
| `attn.qkv_input_quant` | 0.096 | 0.129 | +34.2% | Cold-L2 row (3.04 cold against 2.45 µs warm), PDL-resident on path |
| `attn.o_proj` | 0.290 | 0.319 | +10.1% | Cold-L2 rows at m <= 16 (fresh 6.0-7.4 µs against 5.0-6.5 µs on path) |
| `attn.kv_append` | 0.088 | 0.111 | +26.4% | Cold-L2 row (2.30 cold against 1.42-1.59 µs warm) |
| `epilogue.logits_all_gather` | 0.019 | 0.029 | +56.6% | There is no all-gather kind. The all-reduce curve's ~27 µs floor stands in. |
| `attn.ar_norm` | 0.304 | 0.265 | -12.8% | The same row reads 1 µs short only after o_proj. This is context, not a row or shape error. |

On the `moe.routed` padded rows:
- vLLM routes every padded row: TRT-LLM's monolithic routing uses no `is_padding` mask, which only DeepEP v2
  honors (`fused_moe/layer.py:313`).
- Those rows hold stale input ids and an uninitialized attention output (`model_runner.py:1405`,
  `attention.py:528`), so their experts cannot be derived.
- The capture shows a padded step costs about one extra distinct token. Charging real tokens only would put
  decode at -1.7%; the arch keeps the full padded count as an upper bound.

- `max_num_seqs` 100 replaces c256;
- prompts scale to a 131072 context for cases 06, 11 and 12;

The per-step host time has two parts:
- **PIECEWISE replay at c100 (01, 02).** Decode steps of 97-100 requests pad to 104, which has no FULL key at
  `max_num_seqs` 100, so they replay PIECEWISE. That adds CPU launch time each step: measured D96 → D97 is
  +0.76-0.83 ms, against 0.20-0.38 ms simulated. The measured duty-cycle multiplier is 1.118 / 1.132 on these
  two cases, against 1.009-1.034 on the others except case 10 (1.085).
- **Client round trip (04, 09).** Requests re-enter 2-3 steps late: first_output_wait sits 12-30 ms above the
  engine TTFT.

`diverse_100` simulation shows.

- E2E on 11 and 13.

## Changes that reach other models

| Change | Effect on other models |
|---|---|
| **FULL-decode cap** (`simulator/src/arch/cudagraph.rs`) | The shared helpers moved there from the GLM-5.3 arch file. Inkling gains `max_num_seqs` (default 1024): a uniform decode past the largest capture size within it prices attention unpadded and runs the sinks inline (PIECEWISE). See below. |
| **o_proj rows** | The five `single_gemm` / `torch_linear_vllm` rows at n 4096, k 2048, m 1-16 changed on `main` (values in [PR.md](PR.md#dependencies)). They had come from the upstream 3f667d7 profiler image and were re-measured on the serving fork's image (job 6408). See below. |
| **`fa4_varlen_projection.rs`** | `rel_bias_attention`'s batch projection moved behind an `Fa4VarlenCall` trait. It gained opt-in `whole_waves` and `context_breaks` hooks, which `rel_bias_attention` does not use. A differential test over 14,400 random batches (144 configs) is bit-identical, and Inkling timing-predict outputs are unchanged. |
| **`Nvfp4MoeLocalWorklet.activation_format`** | Inkling and GLM-5.2 pass `None` and are unchanged. |
| **`nvfp4_fused_moe` `activation_format` and `#[compute_dtype_override]`** | Unset for every existing backend and absent from identities. The Optimality analyzer reads a set override first. |
| **`kv_cache_append` `head_dim_v`** | Optional (`optional_arg(same_as=head_dim)`): stored NULL and kept out of `args_hash` when unset, so existing rows keep their keys and no migration runs. `merge-db` merges tables with and without the column. |
| **`all_reduce_residual_rms_norm` grid** | The PDL boundary and the one-shot / two-shot bracket apply to `flashinfer_mnnvl` only, so trtllm rows are not resampled. |
| **IMEX channel** | `KernelProfilerSpec.imex_channel` adds `--device nvidia.com/imex-channel=0` only for the flashinfer_mnnvl backends. Other backends' container argv is unchanged. |
| **model.work** | GQA `v_head_dim` and `attention_sinks`, `SlidingWindowGQA`, `capped_cumulative` moved out of `inkling_rel`, and FP8 `ignored_layers` / MXFP4 in `quantization.py`. Existing goldens pass. |

**FULL-decode cap, cross-model check.** The new binary was run against the previous one on three
`run_config`s:
- Inkling-NVFP4 campaign cases 10 (5,327 iterations) and 01 (217);
- GLM-5.3-Flash-NVFP4 DP-attn/EP c512 (123,145 iterations).

Each is bit-identical per iteration. Inkling's FULL decode sizes are all at most 1024, and vLLM's default `max_num_seqs` keeps every Inkling step
at or below 1024 requests. The cap would move an Inkling prediction only under an explicit
`max_num_seqs` below the largest capture size, with decode steps above it. The GLM archs take no FULL /
PIECEWISE decision.

**o_proj rows, cross-model check.** A preset index built against a DB copy without the five rows shows which
public members read them: 78 GLM-5.3-Flash members (FP8 and NVFP4, TP4 and TP8, the `kda_dsa_moe`,
`pp_kda_dsa_moe` and `dp_attn_ep_moe` arches), plus MiMo. GLM-5.3-Flash TP4 campaign case 12 (c1 decode,
29,328 iterations) moves -0.77% in summed iteration time between `main`'s DB and this branch's. The DP8 c512
decode run is identical, since its steps never reach m <= 16.

## Modeling choices

- **Padded rows in the routed MoE are charged in full.** This is an upper bound; see Check 1.
- **Weight-only MoE through the shared worklet.** `activation_format` drops the quant leaf. There is no
  MiMo-only MoE worklet.
- **Fused all-reduce only.** Steps above the fused cap, and TP sizes with no fused all-reduce, are refused
  rather than priced on vLLM's unfused fallback.
- **All-gather as all-reduce.** There is no all-gather kind.
- **`fp8: true` is required.** The arch has no BF16 variant.
- **The campaign keeps the multiplier at 1.0.** Deployment presets carry the recommended 1.1103.

## Known gaps and follow-up

- **`diverse_100` decode +6.18%** (above 5%). It comes from the padded-row MoE charge and from the router,
  quant, kv_append and o_proj rows. Each fix needs approval:
  - a padded-row rule (not derivable from vLLM);
  - warm-L2 or graph-replay timing for small launches (a profiling-method change for every model).
- **Per-step host time** in campaign cases 01, 02, 04 and 09. The recommended multiplier carries it in
  deployments; the simulator has no per-step PIECEWISE or client-RTT term.
- **`torch_linear_vllm` provenance.** Other rows of this backend may also come from the upstream image. Only
  n 4096 / k 2048 at m <= 16 was re-measured, and the m = 32 row re-measures at 6.14 µs against 4.99 µs
  stored.
- **Shared MoE necessary work.** `MatmulGroup.loaded_instances` charges uniform expected expert hits, so with
  corpus routing R6 exceeds R5 at the routed MoE (0.62 GPU·s on the verification run). This affects every MoE
  model.
- **No all-gather kind.**
- **Not modeled:** sampling, MTP, vision and audio.

## Reproduce

From the repository root. For the campaign, set `PACK=presets/alignment/mimo_v26_flash_b200_tp4` and point
`OUT` at a fresh experiment directory:

```bash
uv run python -m launcher alignment-campaign check --pack "$PACK"
uv run python -m launcher alignment-campaign render --pack "$PACK" --host <host> --out-root "$OUT"
for phase in profile_workload profile_nsys timing_predict; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign label --pack "$PACK" --out-root "$OUT"
for phase in analysis_kernel simulation analysis_e2e; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign extract --pack "$PACK" --runs "$OUT" --out metrics.json
uv run python -m launcher alignment-campaign compare --pack "$PACK" --measured metrics.json --markdown
```

Host requirements:
- The profile phases need 4 B200s per case and an IMEX channel (MNNVL).
- The sbatch wrapper exports the JIT and autotune cache directories and
  `FLASH_ATTENTION_CUTE_DSL_CACHE_ENABLED=1`.
- vLLM's ZMQ IPC path (`TMPDIR` plus a uuid) must fit 107 bytes.

`diverse_100`: `logs/20261012_6_mimo_diverse100_final/run.sh` runs Check 1 and Check 3 on CPU.

The public presets are checked by building every member against the committed profile.db, with no GPU:
