This is review evidence for the `qwen4_exp_vllm_nvfp4_gdn_qsa_moe_speculative` arch on
`nvidia/Qwen3.8-Flash-Next-NVFP4`. It covers:
- what the simulator models;
- how it was checked against vLLM captures;
- what is still open.

It is not an accepted baseline. Tolerance failures and the known gaps below stay explicit, and no golden has been
recorded.

## How each model feature is modeled

- **Precision is read from the config.** `qwen4_exp_model_cfg` reads ModelOpt `MIXED_PRECISION`:
  - the body's routed experts are NVFP4 (group 16);
  - the MTP layer's experts are W8A8 FP8 with 128×128 blocks;
  - the PLE table is FP8 per-tensor when the map lists it and BF16 when it does not;
  - every other linear, both heads and the token embedding are BF16 `F.linear` / `F.embedding`.

  Any other mix is refused. There is no Inductor in this server, so no norm, activation or quant is fused into a
  neighbour.
- **GDN / QSA hybrid.** `text_config.layer_types` sets the mixer of each layer: 36 Gated DeltaNet layers and 12
  QSA layers, folded as 1 / 1 / 34 / 12 by (mixer, HC entry, PLE).
  - **Gated DeltaNet** (`vllm_bf16_gdn_spec_local`) prices the verify path vLLM runs:
    - a pure verify step runs the spec `causal_conv1d_update` and `fused_gdn_decode_post_conv_mtp`, the fused
      verify recurrence plus gated RMSNorm (`gdn_recurrent_decode_gated_norm`);
    - a mixed step splits spec and non-spec rows with `index_select`, runs the conv and sigmoid-gating recurrence at
      the verify width, the FlashInfer chunked delta rule for the prefills, the state gather / zero / scatter,
      and merges with `index_copy_`;
    - a one-token non-spec decode beside spec decodes runs as a one-token prefill (`gdn_attn.py`);
    - more than 8 tokens per request, or an unsupported head ratio, takes the unfused path, priced, not refused.
  - **QSA** (`vllm_qsa_attn_local`, `SparseGqaIndexerOp`, `SparseGqaAttentionOp`):
    - BF16 `qkv_proj`, the fused QK norm + partial RoPE + gate, and the FP8 KV append (`reshape_and_cache_flash`)
      at the rows the launch covers;
    - the indexer: prepare, decode or prefill logits over the compressed keys, top-k, expand. The top-k takes the
      cooperative kernel at 64 rows or fewer and the persistent kernel above, as vLLM's dispatch does. The
      cooperative kernel runs one CTA cluster per row in a single wave, so it is priced at the longest request;
    - sparse paged attention (split-K and merge). A row below the 2048-token budget attends its whole context and
      a row at or above it attends the budget, so one call is priced as the row-weighted mean of two cells, one per
      context group;
    - the MTP recurrent passes run the full indexer: the checkpoint has no index sharing for MTP iterations.
- **Gated hyper-connections** (`hc_mix_local`). The residual is 4 streams. Each module runs:
  - the entry norm: `hc_combine_norm` (the delayed combine fused with the per-stream Gemma RMSNorm), or
    `grouped_rms_norm` where no combine is pending (layer 0 and the module right after the PLE block);
  - the merged down + inject GEMM (k 10240, n 336), `scaled_silu`, the up GEMM (n 10240, k 320) and
    `hc_gate_mix`.

  The final mixer drops the injection columns. model.work counts its down, up and mix only at the sampled positions,
  because the drafter reads the combined multi-stream state and only the head reads the mixed stream.
- **PLE n-gram embedding** (`ple_local`, layer 1).
  - `ple_ngram_ids` (int32 ids and context, as production passes them), then one row gather per n-gram head from
    the FP8 table: 16 heads of 160, 320,001,536 rows. The row count is derived from the config's primes, exactly
    as the fork builds the table.
  - The table sits in pinned host memory and is read by the fork's UVA Triton kernel
    (`embedding_row_gather` / `vllm_triton`, `host_uva`). `table_rows` is an exact key: the gather slows 4.4x from
    a 1M-row to this table at 2048 tokens (*measured*). With `ple_table_residency: device` the gather is
    `F.embedding` (`torch`).
  - The pending `hc_combine`, the finalize copy and dequant, the BF16 `kv_proj` (n 12800), `ple_gate`, and
    `ple_short_conv` (kernel 4, dilation `ngram_size` = 3) in decode, spec or prefill mode.
  - vLLM prefetches the lookup on a side stream before layer 0. The lookup is priced serially in layer 1; the
    offload costs no host compute, since the gather is a GPU kernel over UVA.
  - One PLE layer is accepted. A second would bring its own, larger table.
- **MoE with an aux-stream shared expert** (`vllm_nvfp4_moe_shared_stream_local`).
  - The BF16 router (2560 to 512) and the NVFP4 TRT-LLM fused MoE with `renormalize_naive` routing (softmax top-10,
    renormalized, BF16 logits, no groups, no bias).
  - The shared expert (`bf16_gated_shared_expert_local`): BF16 gate_up, vLLM's CUDA `silu_and_mul`, down, the
    `[hidden, 1]` gate GEMV, sigmoid and the broadcast multiply.
  - At T <= 256 the shared expert runs on the aux stream, launched before the router
    (`VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD`), so the block is
    `Sum[Parallel{Sum[router, routed], shared}, add]`. Above 256 it runs inline.
  - Expert demand comes from the `diverse_100` token corpus: 135,144 accepted tokens × 49 layers (48 body and the
    MTP layer).
- **MTP k = 3 with a recurrent draft.** The drafter (`mtp_fc_prelude_local` and one QSA decoder layer with FP8
  block experts, `vllm_fp8_moe_shared_stream_local`):
  - step 0 runs over every row the target scheduled: the device token embedding, the embedding and hidden norms,
    `fc_embedding` and `fc_hidden`, the layer, the final mixer, and the greedy head on the request endpoints;
  - one endpoint pass per further draft position, compiled once and folded `draft_tokens - 1` times, at one query
    row per request, replaying the drafter's FULL graph at the padded request count;
  - the drafter reuses the target's embedding and lm_head (`mtp_use_dedicated_embeddings = false`).
- **Rejection sampler.** The target head scores one row per prefill request and every verify row, in BF16 logits.
  The logits statistics and the rejection resample are elementwise placeholders priced as one streaming pass over
  each logits row (496,640 B), as the real many-CTA kernels are memory-bound reads. The draft head adds the greedy
  argmax.
- **CUDA graphs.**
  - A uniform verify step (no prefill, no clipped verify) replays a FULL graph. The graph pieces, QSA, the n-gram
    ids, the PLE lookup and its finalize copy run at the padded rows. The GDN verify kernels and the PLE short conv
    skip padded requests, so they are priced at the real ones.
  - A step with a prefill of at most the largest capture size replays PIECEWISE: the graph pieces run at the padded
    rows and the eager breaks at the real rows. Larger steps run eagerly.
- **Engine prep** (`engine_prep_local`): input prep, the sparse-attention metadata and the Mamba align pre-copy are
  elementwise placeholders with byte rates from the arch config.
- **Speculative scheduling.** Acceptance per draft position and per output position comes from each case's own
  workload pass (`acceptance_by_position.json`; tokens per round rise from about 2.4 below 128 output tokens to
  3.3-3.9 past 1024, *measured*). A verify that would cross `max_model_len` is clipped to the rows that keep its
  sampled position inside the limit. QSA classes a clipped verify as a prefill; the GDN and PLE conv metadata keep
  it a spec decode while it carries a draft, and a one-row clip is a plain decode.

### KV accounting

vLLM's hybrid allocator sizes one block so that one QSA KV page holds the largest Mamba-style page
(*catalog*: "Setting attention block size to 3200 tokens"):
- The GDN state page is the conv taps (`conv_kernel - 1 + k` rows) plus the FP32 SSM state: 3,268,608 B, padded
  0.25% to 3200 × 1024 B.
- One block stride is 43,929,600 B: the KV of the 13 QSA layers (12 target, 1 MTP) and their compressed index keys.
- The 36 GDN layers fill 3 strides per block; the PLE conv state and the BF16 raw-key ring of the indexer take one
  stride each. The ring is never prefix-cached.
- A recurrent state keeps `1 + k` = 4 copies: the running state and one per speculative token.

`kv_cache_layout` derives all of this from the config. At 79.80 GiB the pool is 1950 blocks. vLLM's concurrency
estimate charges a max-length request 62 blocks: 41 KV, 3 × 5 GDN, 5 PLE and 1 ring. The fifth state copy is align
mode's previous-step block. The simulator reports 31.45x at 131072 tokens, as vLLM logs (*simulated*, *measured*).

A running request holds the 4 declared copies, not 5: vLLM's `MambaManager` frees the previous step's block the
step after a block boundary. A short request holds 18 of the 1950 blocks, so at most 108 run at once, which is the
captures' peak (*derived*, *measured*).

Prefix caching runs the GDN and PLE state in align mode. A non-final prefill chunk ends on a 3200-token block, and
no chunk runs past the prompt's last cacheable block. Because the MTP drafter reads target hidden states, vLLM
drops the last prefix block for it, so that last checkpoint sits one block earlier.

## Kernels

How the kernels were profiled:
- Each new kind is profiled on B200 through the serving fork's public custom ops, with a PyTorch reference check.
- Grids are generic: tokens 1-8192 (16384 rows for the indexer top-k), batch 1-256, context up to 131072. Row keys
  hold model geometry and dtypes only.
- Eager glue is timed in the serving fork's environment (the `_vllm` backend twins), because those launches must
  come from the serving build.

Notes on the rows:
- The top-k time depends on the score distribution, so the rows use seeded normal scores (`uniform_random`).
- A prefill-table attention row is one request whose rows share one block table on consecutive pages, as in a real
  prefill chunk. Rows as separate requests ran 7-9% slower on captured `diverse_100` mixed steps, and the shared
  form matched the capture to 0-5% (*measured*).
- The GDN verify batch axis is dense over 1-8, because one CTA per (request, value head) crosses SM-wave boundaries
  that powers of two straddle.
- `F.embedding` takes a small-index path at 16 indices or fewer, about 5x the 17-index launch, so the token grid
  holds 17.
- The shared expert's `act_and_mul` is vLLM's `act_and_mul_kernel`: 4.11 µs captured at 2048 tokens, 4.87 µs in the
  `vllm_cuda` row (*measured*).

How to read the per-operation rows. `measured_ms` is the operation's slice of the per-iteration busy union: launches
are swept in start order and each is credited only with time past the running cover end. Where kernels overlap,
across streams or within one stream under PDL, the first launch gets the overlap, while the simulator prices each
leaf in isolation. So:
- decode `moe.shared.*` reads -100%: `shared.gate_up` launches before the router on the aux stream and takes the
  overlapped head. The block as a whole is the comparison that matters;
- decode `moe.routed.input_quant` and `moe.router` read high for the same reason;
- `hc.silu`, `hc.gate_mix`, `hc.combine_norm` and `gdn.ba` start inside their predecessor under PDL and are credited
  only their exclusive tail. Their raw kernel durations match the rows.

The causes of the misses:

- **Mixed-step host launch time.** A PIECEWISE mixed step issues about 2,100 CUDA API calls, and preprocess makes
  one pageable 8-byte H2D copy followed by
  `cudaStreamSynchronize`. Under nsys the GPU idles 1.7-30.5% of a mixed step across the cases checked, mostly in
  the forward and preprocess host phases; a pure-decode FULL-graph step idles 0.3-17% (*measured*,
  `logs/20261013_13_qf_host_stall/idle_summary.txt`). The simulator has no host-time mechanism; the median
  multiplier 1.0881 covers it on average, so cases whose steps expose more host time read fast (02) and
  single-request cases read slow (11, 12).
- **Per-request acceptance spread.** The by-position chain fixes the mean, but a few requests accept far fewer
  tokens per round than their bucket. In vLLM those last finishers drain in pure-decode steps the simulation does
  not run, which shortens the makespan and raises output throughput; iterations drop and the mean decode batch,
  prefill and scheduled KV rise. Short outputs whose prompts accept less also need more rounds than the bucket
  predicts. Replaying each request's measured acceptance (observed-conditioned, `PR.md`) brings the iteration count
  of 07, 08 and 18 within 1.4% and cuts the out-of-tolerance count from 86 to 54.
- **Server TTFT low.** vLLM's async scheduler takes about twice as long from first schedule to first token as the
  simulator. In the queued cases the simulator also drains faster, which shortens the queue.
- **Kernel high in single-request prefill (case 11).** Its mixed stage is almost entirely 2048-token single-request
  prefill steps, where the mixed `fused_moe` and the m=2048 BF16 GEMMs read high (Known gaps).
- **Workload-structure 1% bands.** The pure-decode iteration count follows the acceptance spread. In saturated
  bursts (01, 02) vLLM refills freed slots over more, smaller prefill steps; async scheduling seeing completions one
  step late would explain it, but this is not checked.

The fork's per-iteration log is shifted by one to two steps (Known gaps). It moves time between neighbouring
logged iterations but conserves the total, so it affects per-step cycle comparisons, not E2E.

## Modeling choices

- **Multiplier 1.0881, the median of the 21 captures' recommendations.** It absorbs the mixed-step host launch time
  as a uniform scale. Per capture the value spans 1.030-1.482 with the step shape (PR.md), so a single value
  under-corrects bursty small-chunk cases and over-corrects single-request ones. A host-time model needs its own
  design (Follow-ups).
- **Real requests in FULL-graph GDN verify and PLE short conv**, because padded requests skip them. The graph
  pieces, QSA and the PLE lookup run at the padded rows.
- **The PLE lookup is priced serially.** In a mixed step no main-stream kernel runs during the lookup, so serial
  pricing is what is measured. In decode it hides behind layer 0's HC kernels; the serial sum over-prices it by
  about 14 µs per decode step (*measured* exposure about 2 µs of 5-14 µs).
- **One context-group split for QSA attention.** Rows of one call are priced in two groups, below and at the
  budget. Spread of contexts within a group is not modeled (Known gaps).
- **Corpus routing, folded across layers.** Per-layer expert histograms are sorted by rank and averaged, and one
  histogram is priced per MoE call.
- **Sampler and engine prep as byte placeholders.** They are launch-bound groups of small Triton and torch kernels.
- **The arch refuses `num_layers` overrides and more than one PLE layer.** The schedule comes from `layer_types`.

## Known gaps and follow-up

- **Mixed-step host launch time** (PIECEWISE, about 2,100 CUDA calls plus the preprocess sync). Not modeled; the
  multiplier ships at the 21-capture median 1.0881. This is the main E2E residual.
- **The alignment fork's per-iteration log is shifted.** `observed_start` (`core.py`, `step_with_batch_queue`,
  around `future.result()`) is taken after the next batch is dispatched. Decode steps logged just before a mixed
  step absorb that step's time, and totals are conserved; in most cases 70-100% of the apparent decode "stall"
  excess sits in the two decode steps before a mixed step (*measured*). Recompute steps after preemption are logged
  as decode (`vllm/v1/utils.py`). This affects per-step cycle comparisons, not E2E.
- **Mixed-step `fused_moe` reads high.** Tactic, L2 and power were ruled out, each within 0.7% (*measured*). Two
  shared mechanisms remain:
  - the layer fold: averaging rank-sorted per-layer histograms costs 3.4% (2048 tokens) to 7.0% (1152 tokens) more
    than the mean of the 48 real layers;
  - the corpus records generated tokens only, while a mixed step is one contiguous prompt chunk that activates fewer
    experts (inferred +5-8%; prompt routes are not captured).

  The profiler's expert weights are also uninitialized (`torch.empty`); random weights run 3.7-10.5% slower.
- **QSA attention load imbalance.** A mixed step whose rows have widely varied contexts reads low: one launch's time
  follows its longest rows, which a two-group mean does not carry.
- **`gdn.qkvz` and `qsa.qkv_proj` at m=2048 read high.** Serving runs `nvjet_sm100_tst_128x256_64x6_2x1_2cta` in
  97.7 µs; the row is 110.3 µs. The profiler's back-to-back launches hold the GPU at its power limit, a duty cycle
  serving does not reach (other m=2048 GEMMs land within -6% to +5%).
- **`prep.input_prep` reads near zero.** It is launch-bound (about 78-161 small launches per step) and priced as
  three byte placeholders.
- **Decode MoE shared / routed contention.** Routed kernels run longer than their isolated rows while the aux-stream
  shared expert shares the SMs, and the shared chain ends after the routed finalize in most blocks. The
  `Parallel{max}` structure is right; the contention is not modeled.
- **PDL attribution.** HC and split-K GEMM kernels start inside their predecessor. Per-operation deltas move between
  neighbours; judge them as a block.
- **Cold-L2 glue.** Glue rows are measured with L2 cleared before each launch, while in serving their inputs were
  just written. Mixed-step glue runs 10-20% faster in the capture.
- **Per-request acceptance spread** (above). The tail is not reproduced without observed conditioning.
- **Async-scheduler first-token latency** is not modeled; TTFT reads low.
- **`rms_norm` / `vllm_gemma_native` below 32 rows** over-predicts up to 1.27x (MTP decode at hidden 2560).
- **`mamba_align_precopy` assumes prefix caching is on.** The arch has no prefix-caching flag.
- **One PLE layer** is supported.
- **Not modeled:** the post-step bookkeeping launches, vision, and the plain (non-spec) GDN decode path, which this
  deployment does not run.

Follow-ups that cross models and need a decision:
- the Analyzer per-step timestamp fix for the fork's log shift;
- a generic host launch-cost model for PIECEWISE steps;
- fused MoE: single-layer histograms instead of the fold, prompt-route capture in the token corpus, and initialized
  profiler expert weights;
- `coerce_args` bool handling, which leaves a stored "0"/"1" as text, for about 20 kinds;
- a neutral vLLM helper module for the shared arch helpers;
- a prefix-caching flag on the arch, for `mamba_align_precopy`.

## Reproduce

From the repository root. Set `PACK=presets/alignment/qwen38_flash_next_nvfp4_b200_tp1` and point `OUT` at a fresh
experiment directory:

```bash
uv run python -m launcher alignment-campaign check --pack "$PACK"
uv run python -m launcher alignment-campaign render --pack "$PACK" --host <host> --out-root "$OUT"
for phase in profile_workload profile_nsys timing_predict; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign label --pack "$PACK" --out-root "$OUT"
for phase in analysis_kernel simulation analysis_e2e; do
  uv run python -m launcher alignment-campaign run --pack "$PACK" --out-root "$OUT" --phase "$phase"
done
uv run python -m launcher alignment-campaign extract --pack "$PACK" --runs "$OUT" --out metrics.json
uv run python -m launcher alignment-campaign compare --pack "$PACK" --measured metrics.json --markdown
```

The CPU phases run with `--no-gpu` and `CUDA_VISIBLE_DEVICES=""`. Host requirements for the profile phases:
- one B200 per pass, about 51 GB of pinned host memory for the PLE table, and `--max-num-seqs 256`;
- each Slurm job needs its own port and scratch, with starts staggered;
- warm the JIT and autotune caches with one pass per chunk size before the others start;
- vLLM's ZMQ IPC path (`TMPDIR` plus a uuid) must fit 107 bytes;
- the token-corpus pass needs the fork at `e1423a4d` to record the MTP drafter's routes.

The public presets are checked by building every member against the committed profile.db, with no GPU:

```bash
just test-presets
```
