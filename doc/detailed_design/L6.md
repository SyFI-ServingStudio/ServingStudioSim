# L6 — Orchestrator

L6 models serving topology: it routes arrivals and protocol messages across
pools of L5 workers. It owns pool-local placement, inter-pool phase flow,
cross-worker barriers, and the shared GPU/transfer cluster. It does not evaluate
model cost or mutate request/KV lifecycle inside a worker.

## Role and boundary

- **Below:** typed L5 worker protocols and build recipes.
- **Here:** deployment → pool routing and cross-worker coordination.
- **Above:** L7 drives one erased `Flow` and serializes facts from its cluster.

No code above L6 holds a worker reference.

## Deployment → pool → group → worker

- **Deployment** fixes the serving protocol: unified, PD, AFD, or PP. One deployment
  builds one L6b `Flow`.
- **Pool** is one routing role. Unified has `main`; PD has `prefill` and
  `decode`; AFD has `attn` and `ffn`; PP has `stage`.
- **Group** is one homogeneous `(gpu, replicas, arch, worker)` provider slice.
  Multiple groups are represented in config but current builders require one
  group per pool.
- **Worker** is one L5 replica on the GPU extent reported by its L4 model.

The pool is L6's main abstraction boundary: L6a coordinates within one role;
L6b routes between roles.

## L6a and L6b

### L6a — pool-local controllers

A controller owns worker instances, placement/routing state, wakeup filtering,
and worker-event collection. It translates worker events into the protocol
consumed by its flow or sibling controller.

### L6b — deployment flow

L7 sees only:

```rust
trait Flow {
    fn on_arrival(&mut self, request: Request);
    fn tick(&mut self, now: Time) -> Vec<OrchAction>;
    fn cluster(&self) -> &SharedGpuCluster;
    fn background(&self) -> BackgroundWork; // default: none
}
```

`on_arrival` inserts the request into the shared store before routing its id.
`tick` drives due pool work and returns deployment-level actions; current flows
surface request completion. `cluster` exposes the shared registry/transfer oracle
for L7 metadata and logging setup. `background` reports work the flow owns that
the request ledger cannot see (RL training): L7 does not end a run while it is
outstanding, and the stuck watchdog counts its finished units as progress.

The deployment module is the single construction and `dyn Flow` erasure point.

## Shared GPU cluster

`GpuCluster` combines facts that must agree across all pools:

- a dense global `GpuInfo` registry;
- worker-owned communication groups;
- the transfer timing oracle and network-event logger;
- static per-worker/per-partition KV capacities for `run_meta.json`.

Each L5 build recipe allocates its GPU block and registers its KV/communication
facts during construction. PD and AFD workers retain the shared handle for
runtime transfers. The flow owns the shared cluster handle; L7 only borrows it.

This removes the former two-phase “invent inventory, then build workers” path:
the component that knows the real model extent registers it exactly once.

## Production flows

### Unified

`SimpleDpPoolController` owns one pool of iter-wise workers. It supports
`LeastQueued`, `RoundRobin`, and `TraceDirected` placement and ticks only workers
whose next wakeup is due. `SimpleDpFlow` maps worker completion to
`OrchAction::Complete`.

**Trace-directed placement.** The trace's `placement` tag declares a
`target_worker` per row (`RequestCore::placement`, separate from the scheduling
contract because L6 routing reads it and L5 admission does not). `trace-directed`
obeys it; a row without one is refused. A load policy refuses a placed trace
unless the pool says `trace_placement: ignore`, which is how a counterfactual arm
re-places the same work on purpose. A target that has been retired follows the
pool's `redirect` chain to the worker its work moved to.

**Migration (recompute, not transfer).** A pool may carry a `MigrationPolicy`
(`migration_*` pool keys; `off` builds none and leaves the tick path untouched).
The policy reads a `WorkerLoad` snapshot each tick before the workers run and
returns `MigrationOrder`s naming workers or prompt groups, never requests:

- `Consolidate { src, dst }` — `active-batch-below`: drain the emptiest worker
  under the threshold (once it has peaked above it) onto the busiest one.
- `Scatter { src, dsts, retire_to }` — `train-group-{samples,active}-below`: a
  block of `workers_per_train_group` workers whose in-flight samples (unfinished
  groups × `group_size`) or summed active batch fall under the threshold hands
  each resident group to the emptiest live worker of another block and retires.
- `MoveGroup { src, dst }` — the same release with `migration_group_latency_ms`
  > 0: the block hands one group over every latency interval and keeps decoding
  the rest, retiring only after its last group leaves.

The controller turns an order into L5 drain calls (`MigratableWorker`) and one
`WorkerMsgCommon::Resume` per drained request to the destination, which
re-prefills `prompt + emitted` through its retraction path (TTFT is kept;
recompute lands in `reprocessed_prefills`). Retiring a worker sets
`redirect[src]` and drops its retained prefix tier. Destinations exclude retired
workers, blocks already released this tick, and workers whose own work has run
dry. Prompt groups (`group_by: id-block` blocks of `group_size` ids, or
`group_by: session` whole conversations whose round count the trace declares)
live in one `GroupLedger` shared by migration and training.

**RL training.** `training: streaming-work-steal` adds a `TrainingPool`: one
`TrainChunkWorker` per train group (the same blocks migration releases). A group
enters one shared queue when its slowest member completes; a block starts
training the moment all of its workers are empty; each free block grabs groups
under slime's graduated tail split (`train_groups_per_grab`,
`train_tail_threshold`, `train_expected_groups`). Chunk cost is a calibrated
`train_tokens_per_s` plus `train_chunk_overhead_ms` (no training kernels exist in
`profile.db`), logged to `cost_log` under pool tag `main.train`, section
`train`, one `calibrated` leaf. Migration and training are unified-only; PD, PP
and AFD pools refuse them, and PD/PP refuse `trace-directed`.

`UnifiedWorkerFactory` shares one `Arc<Model>` and `SharedRequests` across
replicas and invokes the family-local L5 `build_*_worker` recipe selected by the
deployment.

### Prefill/decode disaggregation

`PdFlow` composes two `SimpleDpPoolController`s:

```text
arrival → prefill worker → PrefillDone
        → decode handoff/pull → PullComplete ack
        → decode completion
```

The flow ticks the prefill producer first, so a same-timestamp handoff can reach
decode in the same L6 tick. Pull acknowledgement is routed back to the exact
source prefill worker holding that request's KV capacity.

### Attention/FFN disaggregation

AFD uses protocol-specific controllers rather than forcing task aggregation
through the simple-DP request surface:

- `AfdAttnPoolController` owns sticky least-estimated-KV request placement,
  per-slot all-attention-worker barriers, aggregation into FFN tasks, scatter
  back to attention workers, and terminal release.
- `AfdFfnPoolController` routes already-aggregated `FfnTask`s to FFN workers and
  returns section events.
- `AfdFlow` orders the two controllers and surfaces completed requests.

Every active slot advances across all attention workers in lockstep, including
empty shards. The barrier divisor is therefore the fixed worker count rather
than a changing per-iteration membership set.

### Pipeline parallelism

PP has one `stage` pool whose workers are the stages of `replicas` independent
pipelines; worker `r * depth + s` is stage `s` of replica `r`.
`PpStagePoolController` places arrivals on heads, hands each finished microbatch
to the next stage of the same replica, and reports the last stage's finish to the
head as `MicrobatchExit`. It repeats the pool sweep at one `now` until no worker
emits an event, so a stage hand-off costs no tick. Followers settle before heads
tick, so an exit that happened by `now` reaches its head before the head forms
its next microbatch. Every routed message makes its receiver due immediately.
Activation pulls use the NVLink `p2p_intra` curve.

## Layer invariants

- L7 holds only `Flow`; workers never escape L6.
- Pool controllers own routing and protocol coordination, not L5 component
  composition.
- L5 recipes self-register GPU/KV/communication facts in the one shared cluster.
- Request placement on AFD attention workers is sticky for the KV lifetime.
- A migration policy names workers or prompt groups, never requests; what a
  drained request costs on its destination is L5's recompute path.
- A retired worker never receives new work: trace targets resolve through the
  pool's redirect chain.
- Cross-worker barrier membership and event ordering are explicit protocol
  state, never inferred from queue length.
- The typed `PoolSpec<Arch, Worker>` family prevents crossing unrelated L4/L5
  contract classes.
