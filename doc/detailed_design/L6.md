# L6 — Orchestrator

The orchestrator models the **serving topology**: how a deployment's requests are
routed across pools of workers. It owns request routing and the run's GPU inventory,
and defers the per-iteration cost + request lifecycle to the L5 workers.

## Role and boundary

- **Sees:** pools of workers and the request stream.
- **Doesn't see:** the tick loop, the clock, or trace I/O — L6 is driven by L7. No
  code outside L6 ever holds a `&Worker`.

## The abstraction: deployment → pool → group → worker

A run's topology is a four-level hierarchy; L6 owns the top two levels.

- **Deployment** — the serving shape (unified / PD / AFD). It fixes which *roles*
  exist. One deployment = one L6b `Flow`.
- **Pool** — the set of workers exposing one L6-facing **role**. A pool is the
  deployment's role boundary, not a GPU-type or Rust-worker-type boundary: one
  logical role may mix GPU models. Unified has one pool (`main`); PD has `prefill` +
  `decode`; AFD has `attn` + `ffn`. A role is split into several pools only when the
  flow must route between them explicitly.
- **Group** — one homogeneous slice of a pool: a single GPU type + a `replicas`
  count (the data-parallel fan-out) + an arch (L4) + worker (L5) provider.
- **Worker** — one model replica's execution, running on `gpus_per_worker` GPUs.

The **pool boundary is L6's only abstraction** (Invariant 1): everything above the
worker is routing; everything at or below it is cost + lifecycle.

## Two halves, split at the pool boundary

- **L6a — pool-local orchestration** (inside one pool): build and hold the worker
  instances, pick a worker by placement / load balance, tick them, and collect
  self-tagged `WorkerEvent`s into a caller-owned sink, translating them to
  `PoolEvent`s for L6b. L6a never decides deployment-level phase jumps.
- **L6b — inter-pool deployment flow** (between pools): consume external arrivals and
  L6a's `PoolEvent`s, decide which pool gets work next, and hold any
  deployment-level phase / priority state. **L6b is the only object L7 holds**,
  through the `Flow` trait: `on_arrival(req)` inserts facts into the shared store and
  admits the id; `tick(now) -> Vec<OrchAction>` drives the pools and surfaces
  deployment actions; `inventory() -> &GpuInventory` exposes the occupied GPUs for
  L7 to serialise. `OrchAction` is the deployment-level result L7 consumes (today
  only `Complete { req }`).

## Directory and current set

| Path | Holds |
|---|---|
| `mod.rs` | The `Flow` trait + re-exports (the L7-facing surface). |
| `common.rs` | `OrchAction` / `PoolEvent`, `GpuInfo` / `GpuInventory`, `UnifiedWorkerFactory`. |
| `config.rs` | Pool + group topology: `PoolSpec` / `GroupSpec` / `PlacementPolicy`, generic over the provider types (an iter-wise arch can only pair an iter-wise worker). |
| `impls/simple_dp.rs` | `SimpleDpPoolController` (L6a) + `SimpleDpFlow` (L6b): one pool of identical unified workers. |
| `impls/pd.rs` | `PdFlow`: a prefill pool → decode pool handoff built from two simple-DP pools. |

`simple_dp` is the single-pool DP building block: `SimpleDpPoolController` picks a
worker by `DpPlacementPolicy` (`LeastQueued` / `RoundRobin`) and only ticks workers
whose next wakeup is due; `SimpleDpFlow` maps each `PoolEvent` to an
`OrchAction::Complete`. A pool's workers are stamped by a `UnifiedWorkerFactory`
(identical workers sharing one `Arc<Model>` and one `SharedRequests`), which threads
`gpu_name` / `gpus_per_worker` so L6 can build the run's `GpuInventory` — a flat
`Vec<GpuInfo>` with dense, globally-unique ids that L7 serialises to
`raw/run_meta.json`. `pd` composes two controllers, ticking the prefill producer
first and mapping its `PrefillDone` events to same-tick decode admissions.

## Up / down

- **Above (consumer):** the L7 sim driver calls `Flow::{on_arrival, tick,
  inventory}`; the deployment layer constructs the concrete `Flow`.
- **Below (driven):** L5 workers (`enqueue` / `tick` / `status`) and, through the
  factory, the L4 model.

## Layer invariants

- The pool boundary is L6's only abstraction; nothing outside L6 holds a `&Worker`.
- One deployment binds one `Flow`; a role splits into multiple pools only to route
  between them.
- The provider type parameters on `PoolSpec` / `GroupSpec` enforce the arch↔worker
  contract class.
- GPU ids are dense and globally unique across pools; the flow owns the inventory,
  the controller populates it by `&mut`.
