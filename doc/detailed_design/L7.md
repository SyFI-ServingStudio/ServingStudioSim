# L7 — Sim infrastructure

The deployment-independent heart of the simulator: **one process, one sim thread,
one clock**. L7 loads a workload trace, drives whatever L6 `Flow` it is handed,
emits per-request parquet rows, and stops on a termination policy. It knows nothing
about *which* deployment it runs — it only ticks the `Flow` trait and reads request
lifecycle back from the shared store for logging. Logging may spawn writer threads,
but the modelled loop itself is single-threaded.

## Role and boundary

- **Sees:** a `Flow`, a clock, an arrival trace, the log sink.
- **Doesn't see:** what kind of deployment it drives — that is erased behind `Flow`.

## The sim core (`simulator/src/sim/`)

Two parts:

- **`TraceFrontend` (`frontend.rs`)** loads single-round workload CSV(s) once into an
  immutable, arrival-ordered queue (`id, input_len, output_len, arrival_time`).
  `drain_due(now, emit)` emits every `Request` whose *effective* arrival time
  (`arrival_time / request_rate`) is `≤ now`; a higher rate compresses the timeline.
  The drain loop lives here so a caller can't under-drain by polling once per tick.
- **`run_sim` (`run.rs`)** is the single tick loop, returning
  `anyhow::Result<RunSummary>`.

Each tick, in order: drain arrivals due by `clock` into `flow.on_arrival(req)`; call
`flow.tick(clock)` and write a terminal `request_slo` row for each
`OrchAction::Complete`; take a periodic dense `request_state` snapshot over the
admitted set (so per-segment workload is a plain diff of consecutive snapshots);
check termination (`DrainComplete` / `DurationReached` / `Stuck`, all O(1)); and
advance `clock += tick_dt`. In-flight is tracked from arrival / completion counters,
never by scanning the store each tick. `TickCfg` defaults: `tick_dt` 100 µs (a
deliberate quantisation — per-iteration work is O(events), not O(ticks)),
`snapshot_dt` 100 s, `stuck_threshold` 60 s.

At sim-end, the final `request_state` census remains scoped to admitted requests,
while partial `request_slo` rows cover every arrived request that has not completed.
The latter intentionally includes the never-admitted pending tail so stage logging
preserves queue/backpressure evidence on duration-limited and stuck runs.

Stage-event location denotes the worker that owns the request lifecycle, not every
worker that executes compute for it. In AFD, attention placement is sticky and owns
the request location through Pending, Prefill, Decode, and Done. The FFN Terminal
still advances output-token and completion bookkeeping, but its category transitions
retain the attention owner's `(pool, worker)`; FFN workers therefore have no
request-state series.

`RunSummary` is written to `<log_dir>/summary.json` and rendered to the end-of-run
log lines from the same struct. Every field except `wall_s` / `realtime_x` is
deterministic given a fixed trace + config + cost model; those two are the
simulator's own host-dependent speed.

## The deployment seam (`simulator/src/deployment/`)

The assembly glue at the L6/L7 boundary: it deserialises a structured `RunConfig` and
builds the concrete `Flow` the sim driver ticks. The `deployment` tag is the
top-level switch that fixes, in one choice, the orchestrator (1:1), the pool
topology, and each pool's contract class. The `Deployment` trait exposes
`const NAME`, a `Config` type, and `build(cfg, bridge, store) -> Box<dyn Flow>`;
`build_flow(&RunConfig, …)` is the single dispatch point. `unified`, `pd`, and
the Qwen3 attention/FFN `afd` pairing are wired.

`UnifiedDeployment::build` runs the lower layers in order: take the `main` pool's
homogeneous group; load the dense `ModelCfg` or `MoeModelCfg` selected by the
arch tag; build a `WorkerConfig`; select the arch by its explicit tag
(provider-first, not a `tp_size` dispatch) and run the L4
`build_configs → resolve_configs → build` cascade; then `assemble_flow` wraps the
`Arc<M>` in a `UnifiedWorkerFactory` + `SimpleDpFlow`.
That `Box<dyn Flow>` is the **single `dyn` erasure point** — each concrete model
monomorphises its own flow, so the per-iter cost path stays `dyn`-free.

`AfdDeployment::build` independently builds the attention and FFN layer-wise
models, the profiled cross-pool transfer cost, and an `AfdFlow`. Its L6
controllers own sticky attention placement, section routing, and the layer
barrier; L7 still sees only the erased `Flow`.

## Logging (`simulator/src/log/`)

Cross-layer streaming parquet output under `<log_dir>/raw/`. The design constraint
is that logging must not slow the sim: the sim thread only fills row buffers and
hands full chunks (`STREAM_FLUSH_ROWS` = 8192) over a bounded channel to a background
writer thread that does the parquet encode + ZSTD compression off the critical path.
Files are created lazily on the first non-empty write.

The streams: `request_slo.parquet` and `request_state.parquet` (per-request, opened
by `run_sim` through `LoggerSession`); and, per L5 worker, `cost_log/worker_*.parquet`
(one row per iteration) plus a `cost_manifest/worker_*.json` sidecar written once at
open. The cost_log row carries the per-slot breakdown as **position-keyed parallel
lists** — never slot names; names live once in the manifest, so a consumer
reproduces `total_time_ms` by re-running `CostTree::aggregate` and labels the list
positions from the manifest (keyed by `(pool_tag, worker_id)`).

## The run interface

- **The binary (`main.rs`)** is the L7 CLI: parse the `RunConfig` → `build_flow` →
  `TraceFrontend::load` → open the logger → write `run_meta.json` → `run_sim` →
  serialise `summary.json`. Its subcommands include `run`, `build-cache-only`,
  `dry-run`, `list-params`, and `kernel-query`.
- **The launcher (`launcher/`, top level)** presents all of this as the actual run
  interface: it builds the release binary + the PyO3 env, prewarms the kernel cache,
  expands sweeps into one fully-concrete config per run, validates presets, and
  writes dated log dirs. The default simulation mode and the offline
  `timing-predict` mode both accept YAML or JSON configs; `list-params` exposes the
  Rust-authoritative schema. Alignment is four explicit subcommands: `sim` enters
  the unchanged simulation pipeline, `profile` runs real vLLM+nsys and ends at a
  normalized measured artifact, `timing-predict` pairs completed artifacts only
  after the user supplies the tagged input adapter; it preserves the completed
  simulation's arch, GPU, and per-role backend policy when rebuilding the
  offline CostTree. `analyze` snapshots the user-labeled folded kernel inventory
  before handing its manifest to the top-level analyzer. No stage implicitly
  enters the next one. Both run inputs should reference the same source trace;
  the pairing stage reports a mismatch as a non-fatal warning.
- **The analyzer (`analyzer/`, top level)** is the downstream consumer — a
  standalone crate (no PyO3) that owns statistics/report payloads and Python
  rendering. Simulator subjects read parquet + JSON sidecars; alignment subjects
  consume the manifest produced by the explicit timing-predict stage.

## Layer invariants

- One sim thread, one global clock; the modelled loop is single-threaded.
- `Flow` is the only object L7 holds; the deployment kind is erased at a single `dyn`
  dispatch point.
- Logging never blocks or aborts the sim; a slow writer applies backpressure via the
  bounded channel.
- Cost-log rows are position-keyed; names live only in the manifest (INV-5), and the
  total is reproduced by replaying `CostTree::aggregate`.
