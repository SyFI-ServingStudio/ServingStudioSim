# L5 — Worker composition and cadence

L5 models one mutable serving-worker replica. A worker may own one GPU or a
multi-GPU parallel group. It accepts typed L6 messages, manages request and KV
lifecycle, turns the current work into an L4 cost query, advances local time,
and emits typed events.

This file is the canonical L5 design. The production implementation is
single-track under `simulator/src/worker/`; there is no legacy/composed runtime
switch. Detailed source navigation lives in
`simulator/src/worker/README.md`.

## 1. Boundary

- **Below:** L4 exposes pure model-cost contracts. It does not see queues, KV
  residency, request state, or the simulation clock.
- **Here:** L5 is the first layer with mutable serving state.
- **Above:** L6 owns pools, routing, transfers, barriers, and cross-worker
  orchestration. It does not choose L5's internal components.

L6 drives every worker through the narrow `IterWorker` protocol:

```rust
trait IterWorker {
    type Msg;
    type Event;

    fn id(&self) -> WorkerId;
    fn enqueue(&mut self, msg: Self::Msg);
    fn tick(&mut self, now: Time, events: &mut Vec<Self::Event>) -> Option<Time>;
    fn status(&self) -> WorkerStatus;
}
```

`tick` advances to a local fixpoint at `now` and returns the next useful wakeup.
`None` means quiescent. Events are written into the L6-owned sink and identify
their source worker.

AFD adds only protocol-specific capability views:

- `AfdAttnWorker::estimated_peak_kv` supports sticky least-KV placement.
- `AfdFfnWorker` fixes the FFN task/event pair at the type boundary.

Construction is deliberately outside these traits.

## 2. Composition model

The organizing equation is:

```text
Worker = <KV, Admission<Selection>, Execution> × Shell(cadence)
```

The three components are reusable axes. The shell is a concrete family
boundary, not a fourth generic trait parameter shared by every timeline.
Whole-iteration execution, pull+decode, a layer-slot pipeline, and an FFN double
buffer have different synchronization and completion ownership; forcing them
through one universal FSM would hide the behavior that L5 must model.

The data dependency runs in one direction:

```text
Admission selection/lifecycle ─┐
Shell phase and grouping ──────┼─> Execution input builder ─> L4 ArchInput
KV membership/state facts ────┘
```

This gives three locked ownership rules:

1. `KvStore` never builds an `ArchInput`. Model-input construction belongs to
   the execution axis because only that axis knows the L4 shape.
2. Admission never derives KV bytes or duplicates capacity arithmetic. It asks
   the KV axis for a footprint and calls `fits`/`reserve`.
3. Cadence, transfer overlap, and completion ownership remain in the concrete
   shell. They are not optional callbacks on a universal worker FSM.

## 3. KV resource axis

`KvStore` owns the cross-family resource lifecycle:

```text
footprint → fits → reserve → commit_resident → advance → release
```

The production `FullAttnKv` owns:

- one private `FullAttnPartitionState` per independent attention-DP partition;
- promised reservations and PD-prefill held-KV ledgers;
- runtime resolution of immutable session-prefix declarations;
- one evictable completed-session prefix cache per attention partition;
- sticky request-to-partition ownership;
- strict capacity admission and KV occupancy sampling.

One request remains on its chosen partition for its KV lifetime. A cadence slot
is not a partition: the AFD attention pipeline has multiple slots sharing one KV
partition for one attention worker.

Family-specific capability traits reveal only the observations a cadence needs:

| Capability | Consumer | Additional view |
|---|---|---|
| `IterWorkerKv` | whole-iteration workers | current prefill admits and live decode membership |
| `PrefixKv` | autoregressive prefill lifecycles | prefix plan/reservation, resolved prefill work, retained-session release |
| `SlotPipelineKv` | AFD attention | current request KV, reservation membership, request weight, projected peak |
| `HandoffKv` | PD prefill | hold/complete source KV across a pull acknowledgement |

A capability bound refines the same store; it does not create a second KV
owner. Iteration and slot input builders consume borrowed membership
visitors/slices, so the abstraction does not require cloning the live batch.

The model reports total KV bytes per token and attention shard count through the
execution/model contract. Construction converts the configured attention-memory
budget to token capacity once. Runtime admission uses the KV store's token-space
facts; it does not repeat model-layout math.

### 3.1 Session-prefix ownership and shared capacity

`PrefixInput::Session` is an immutable trace requirement, not a cache-hit fact.
For a fresh suffix `fresh`, declared prefix `declared`, and physically retained
hit `resident`, `FullAttnKv` resolves:

```text
prefill_compute = fresh + (declared - resident)
initial_context = resident + prefill_compute = fresh + declared
```

Admission gates the resolved compute tokens and reserves the full initial
context. Execution receives `(resident, prefill_compute)` from `PrefixKv`; no
runtime hit/miss or resident count is written into request progress. A disabled
or cold cache therefore recomputes the whole declared prefix instead of treating
the declaration as an automatic hit.

The retained prefix cache is a ceiling *inside* the partition's configured
attention memory, never an additional pool. The physical invariant is:

```text
max(active resident + promised + held,
    projected active peak + promised + held)
+ retained prefix
<= total attention KV capacity
```

`fits` may ignore retained entries only because they are evictable; `reserve`
immediately shrinks them to the remaining physical slack. A hit destructively
moves one session entry into the active request, so the current implementation
does not model inter-request prefix sharing or ref-counted pages. Completion
returns the request's physically resident KV to that partition's session cache.
For PD, source KV remains `held` until the decode pull acknowledgement; only then
does it become evictable retained prefix, preventing held and cached ownership
from being counted simultaneously.

Worker selectors expose `prefix_cache_gpu_memory_gb` and an eviction policy for
barebone, HP unified, PD prefill, and AFD attention. Deployment validation
requires the prefix ceiling to lie within `attn_gpu_memory_gb`. PD decode does
not own this retained-session tier; it consumes the exact full-context token
count carried by the prefill handoff. Host tiers and content-level/radix sharing
remain separate future capabilities.

## 4. Admission lifecycle × selection

Admission has two independent responsibilities:

- **Lifecycle:** when a request may move from pending to reserved, resident,
  handed off, or complete.
- **Selection:** which not-yet-started request is considered next.

Pending membership belongs entirely to `PendingOrderPolicy`. A lifecycle owns no
shadow pending queue:

```rust
trait PendingOrderPolicy {
    fn push(&mut self, candidate: AdmissionCandidate);
    fn peek(&self) -> Option<&AdmissionCandidate>;
    fn pop(&mut self) -> Option<AdmissionCandidate>;
    fn remove(&mut self, request: RequestId) -> Option<AdmissionCandidate>;
    // membership/count/accounting observations
}
```

`AdmissionCandidate` freezes selection facts at enqueue. `FifoOrder` uses a
`VecDeque`; `ShortestJobFirst` maintains a heap incrementally and uses a
monotonic enqueue sequence for deterministic equal-work ties. Production
builders currently select `FifoOrder`; SJF is a composition seam, not a
deployment selector.

The production lifecycle families are:

- `LocalPrefillDecodeAdmission<P>` — local prefill, decode, completion.
- `PrefillHandoffAdmission<P>` — prefill, source-KV hold, handoff and pull ack.
- `FreshRequestSlotAdmission<P>` — AFD attention's two-level gate: accept a
  fresh request into `P`, then reserve fitting heads for slot placement.

The last family implements the separate `SlotPipelineAdmission<K>` trait. It
does not expose `form_batch` or `complete_iteration`; the slot shell owns
layer-wise cadence, while paired FFN work owns terminal bookkeeping.

Not every queue in a worker is a selection policy. A queue is a policy only when
its job is choosing which fresh request starts next. Landed PD requests, active
slot work, and FFN tasks are cadence state owned by their shells.

For future chunked prefill, the same distinction is mandatory: the policy owns
fresh requests that have not started; a partition-local lifecycle owns at most
one partially processed `active_chunk`. A partition may contain many resident
prefills over time, but it may not rotate several partial chunks through the
selection queue. Skipping an active chunk must preserve its order and identity.
This is a design constraint, not a currently wired worker.

## 5. Execution axis

Execution owns the model instance, reusable input buffers, input lowering, and
cost buffers. The production sibling traits are intentionally per family:

- `IterModelExecution<K>` — builds `UnifiedArchInput` and evaluates a whole
  iteration.
- `AttentionLayerExecution` — builds `AttnArchInput` for one slot and evaluates
  one attention layer.
- `FfnTaskExecution` — builds `FfnArchInput` and evaluates FFN
  Bootstrap/Bridge/Terminal sections.

Their concrete adapters are `UnifiedIterExecution`,
`AttentionLayerExecutionAdapter`, and `FfnSectionExecutionAdapter`.

The shell treats `E::Input` as opaque. Transfer submission stays in the shell
because its timing and overlap are cadence facts, not model math.

## 6. Production cadence families

### 6.1 Whole iteration

`workers/iter/IterBatchWorker` runs:

```text
form_batch → build/evaluate iteration → complete_iteration → repeat
```

Barebone, head-parallel unified, and PD prefill reuse this cadence with different
recipes.

### 6.2 Pull plus decode

`workers/pd_decode/PullDecodeWorker` coordinates two timelines:

- one serialized KV pull with a bounded landed/in-transit backlog;
- one whole-iteration decode FSM.

A request becomes resident only after prompt KV lands. Pull completion
acknowledges the exact prefill worker holding the source capacity.

### 6.3 Layer-slot attention

`workers/afd_attention/SlotAttentionWorker` combines fresh-request admission
with a private three-slot pipeline. Each slot walks:

```text
Wait → WaitComplete → Pull → PullComplete → Compute → AwaitFlush
```

At most one slot pulls and one computes. L6's all-worker layer barrier releases
`AwaitFlush`, so empty attention shards remain in lockstep.

### 6.4 Buffered FFN

`workers/afd_ffn/BufferedFfnWorker` has no KV or request-admission component. L6
delivers complete `FfnTask`s, and the worker overlaps one incoming gather with
one current section compute:

```text
incoming → pulling_task → computing_task → SectionReady / IterComplete
```

Terminal owns token emission and request completion while preserving the sticky
attention worker as the request's recorded location.

## 7. Current compositions

| Worker selector | KV | Admission | Execution | Shell |
|---|---|---|---|---|
| `barebone` | `FullAttnKv` | `LocalPrefillDecodeAdmission<FifoOrder>` | `UnifiedIterExecution` | `IterBatchWorker` |
| `hp_unified` | `FullAttnKv`, N partitions | local admission with round-robin placement | `UnifiedIterExecution` | `IterBatchWorker` |
| `pd_prefill` | `FullAttnKv` with held ledger | `PrefillHandoffAdmission<FifoOrder>` | `UnifiedIterExecution` | `IterBatchWorker` |
| `pd_decode` | `FullAttnKv` | thin landed-request ingress | `UnifiedIterExecution` | `PullDecodeWorker` |
| `disagg_attn` | `FullAttnKv` | `FreshRequestSlotAdmission<FifoOrder>` | `AttentionLayerExecutionAdapter` | `SlotAttentionWorker` |
| `disagg_ffn` | none | none | `FfnSectionExecutionAdapter` | `BufferedFfnWorker` |

Aliases such as `BareboneWorker<M>` and `DisaggAttnWorker<M>` name concrete
generic compositions; they are not wrapper runtimes.

## 8. Construction and file boundaries

Every production recipe lives in one `workers/<family>/build_*_worker.rs` file.
The recipe must visibly choose its KV, admission policy/lifecycle, execution
adapter, and shell.

Repeated mechanical setup may live in a narrowly named essentials helper:
allocation, capacity derivation/registration, sampler creation, cost buffers, and
shared context. An essentials helper must not choose semantic composition.

Deployments and pool controllers call recipes only:

- unified → `build_barebone_worker` / `build_hp_worker`
- PD → `build_pd_prefill_worker` / `build_pd_decode_worker`
- AFD attention → `build_afd_attention_worker`
- AFD FFN → `build_afd_ffn_worker`

Message/event enums, pool policy, flow barriers, and cross-worker transfer
protocols remain L6 contracts.

## 9. Compatibility and extension rules

Compatibility is capability-based. A combination is excluded only by a semantic
contradiction; “not implemented”, “no preset”, “expensive”, or “the current
worker has another name” are not design-level incompatibilities.

Hard contradictions include:

- a pure FFN shard cannot own decoder KV or fresh-request admission;
- an encoder-only family cannot use the autoregressive decoder-KV lifecycle;
- a no-KV worker cannot expose reserve, handoff, pull, or prefix-KV behavior;
- standard one-token generation cannot silently use draft/verify logits
  semantics.

A missing capability should fail where the concrete recipe is assembled through
trait bounds. It should not be patched with role enums, optional callbacks, or
runtime `match` branches inside shared axes.

SLO/priority changes selection policy, not lifecycle. Prefix reuse is the
`PrefixKv` refinement of the existing KV owner and matching admission/execution
lifecycle; it does not create another KV copy. A future replacement policy that
changes content identity, host tiers, or page sharing must extend that owner
rather than place runtime residency in the request definition.

Add a new shell only when cadence, overlap, synchronization protocol, or
completion ownership truly changes. Otherwise add the smallest new leaf
component or thin adapter and reuse the existing recipe shape.

An unknown variant fits the abstraction when it can be added with:

1. one new leaf component or necessary thin adapter;
2. one declarative build recipe/registration;
3. focused contract and behavior tests;
4. no copied tick loop, pending ledger, KV ledger, or ArchInput lowering.

If those conditions fail, first identify which ownership boundary is wrong;
do not grow a universal “supports everything” trait.

## 10. Preservation and validation

A composition refactor is correct only when it preserves externally observable
simulation semantics:

- request placement and stable selection order;
- admission gates, KV residency, held/reserved accounting, and release timing;
- modeled event ordering, transfer overlap, and completion ownership;
- KV sampling and cost-log row/manifest structure;
- modeled throughput and deterministic summary fields for the same complete
  preset, model config, workload, and profiling database.

Wall-clock runtime and `realtime_x` are host-performance observations and may
vary; they are not modeled-output equivalence fields.

Validation should include scoped unit/contract tests, `cargo check` for the
simulator library, and representative unified, PD, HP/MoE, and AFD runs. When
comparing branches, use the same resolved model JSON and the same filled profile
database; otherwise a configuration/cache difference can masquerade as a worker
semantic difference.

## 11. Layer invariants

- L5 owns mutable serving state; L4 and below remain pure cost queries.
- KV, admission, and execution have one owner each; the shell owns cadence.
- Selection policy is the sole owner of not-yet-started pending membership.
- Request-to-KV-partition placement is sticky for the request's KV lifetime.
- Active/promised/held KV and retained prefix KV share one physical attention
  capacity; retained prefix is the evictable portion of that same space.
- Model input construction lives on the execution/model side, never in KV or
  admission.
- L4-reported cost time advances the L5 compute clock.
- L6 receives pushed typed events; L5 has no drainable event outbox.
