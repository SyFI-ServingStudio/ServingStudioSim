# L5 — Worker composition and cadence

L5 models one mutable serving-worker replica. A worker may own one GPU or a
multi-GPU parallel group. It accepts typed L6 messages, manages request and KV
lifecycle, turns the current work into an L4 cost query, advances local time,
and emits typed events.

This file is the canonical L5 design. The production implementation is
single-track under `simulator/src/worker/`; there is no legacy/composed runtime
switch. Detailed source navigation lives in
`simulator/src/worker/README.md`.

## 1. Boundary

- **Below:** L4 exposes pure model-cost contracts. It does not see queues, KV
  residency, request state, or the simulation clock.
- **Here:** L5 is the first layer with mutable serving state.
- **Above:** L6 owns pools, routing, transfers, barriers, and cross-worker
  orchestration. It does not choose L5's internal components.

L6 drives every worker through the narrow `IterWorker` protocol:

```rust
trait IterWorker {
    type Msg;
    type Event;

    fn id(&self) -> WorkerId;
    fn enqueue(&mut self, msg: Self::Msg);
    fn tick(&mut self, now: Time, events: &mut Vec<Self::Event>) -> Option<Time>;
    fn status(&self) -> WorkerStatus;
}
```

`tick` advances to a local fixpoint at `now` and returns the next useful wakeup.
`None` means quiescent. Events are written into the L6-owned sink and identify
their source worker.

AFD adds only protocol-specific capability views:

- `AfdAttnWorker::estimated_peak_kv` supports sticky least-KV placement.
- `AfdFfnWorker` fixes the FFN task/event pair at the type boundary.

Construction is deliberately outside these traits.

## 2. Composition model

The organizing equation is:

```text
Worker = <KV, Admission<Selection>, Execution> × Shell(cadence)
```

The three components are reusable axes. The shell is a concrete family
boundary, not a fourth generic trait parameter shared by every timeline.
Whole-iteration execution, pull+decode, a layer-slot pipeline, and an FFN double
buffer have different synchronization and completion ownership; forcing them
through one universal FSM would hide the behavior that L5 must model.

The data dependency runs in one direction:

```text
Admission selection/lifecycle ─┐
Shell phase and grouping ──────┼─> Execution input builder ─> L4 ArchInput
KV membership/state facts ────┘
```

This gives three locked ownership rules:

1. `KvStore` never builds an `ArchInput`. Model-input construction belongs to
   the execution axis because only that axis knows the L4 shape.
2. Admission never derives KV bytes or duplicates capacity arithmetic. It asks
   the KV axis for a footprint and calls `fits`/`reserve`.
3. Cadence, transfer overlap, and completion ownership remain in the concrete
   shell. They are not optional callbacks on a universal worker FSM.

## 3. KV resource axis

`KvStore` owns the cross-family resource lifecycle:

```text
footprint → fits → reserve → commit_resident → advance → release
```

The only KV store is `KvCacheStore` (`worker/kv/kv_cache_store.rs`). It owns:

- one private `ResidentPartitionState` per independent attention-DP partition;
- promised reservations and PD-prefill held-KV ledgers;
- resolved per-request prefill context for immutable session-prefix declarations;
- one evictable completed-session prefix cache per attention partition;
- worker-local lookup of the partition retaining a declared session prefix;
- sticky request-to-partition ownership;
- strict capacity admission and KV occupancy sampling.

One request remains on its chosen partition for its KV lifetime. A cadence slot
is not a partition: the AFD attention pipeline has multiple slots sharing one KV
partition for one attention worker.

Family-specific capability traits reveal only the observations a cadence needs:

| Capability | Consumer | Additional view |
|---|---|---|
| `IterWorkerKv` | whole-iteration workers | current prefill admits and live decode membership |
| `PrefixKv` | autoregressive prefill lifecycles | prefill-context preview/reservation, resolved prefill work, retained-session release |
| `SlotPipelineKv` | AFD attention | current request KV, reservation membership, request weight, projected peak |
| `HandoffKv` | PD prefill | hold/complete source KV across a pull acknowledgement |

A capability bound refines the same store; it does not create a second KV
owner. Iteration and slot input builders consume borrowed membership
visitors/slices, so the abstraction does not require cloning the live batch.
Every arch, hybrid or not, runs on this store, so every capability is available
to every layout.

### 3.1 KV accounting

The arch reports its state as a `KvCacheLayout` (L4.md, KV cache layout). At
worker construction `resolve_kv_accounting` (`workers/iter_build_essentials.rs`)
resolves it once into a `KvAccounting`
(`worker/kv/shared/kv_accounting.rs`) against the partition budget, the per-GPU
attention budget times `num_attn_shards()`. The store never sees layout parts;
it asks the accounting for charges in **KV units** of `bytes_per_unit`, the gcd
of every part's entry bytes. A layout of one per-token part therefore counts
plain tokens.

The simulator does not reproduce an allocator. Block ids, hashes, layer grouping
and page unification are engine mechanics; what decides capacity is how each
part grows. The accounting answers:

| Method | Question | Per-token part | Sliding window `W` (`vllm`) | Per-request state |
|---|---|---|---|---|
| `held_while_running(len, step)` | what a running request holds while a step processes `step` tokens | one entry per `tokens_per_entry` of `len` | `min(len, W - 1 + step)` | one state × copies |
| `needed_to_admit(prompt)` | what a waiting request needs free to start (vLLM's whole-prompt gate) | one entry per `tokens_per_entry` of `prompt` | `min(prompt, W - 1 + max_in_flight)` | one state × copies |
| `entry_charge(positions)` | what a retained prefix entry keeps (§3.2) | up to its last position | the `W - 1`-token tails before each position, counted once | one reusable state per position |

Admission reserves `footprint(context, future)`: the larger of
`held_while_running(context + future, 1)` and `needed_to_admit(context)`.
`growth_over`, `transfer_bytes` (PD pull payload), `tokens_fitting`, and
`reserving(units)` (capacity set aside, as PD decode does for its pull budget)
derive from the same charges. A layout with no window, no compressed part, and
no engine block takes a linear fast path, so full-attention archs pay nothing
for the generality.

`ResidentPartitionState` caches each decode's charge and adds
`held_while_running(new) - held_while_running(old)` per step; once every window
is full only the per-token parts keep growing. `current_kv` stays the context
tokens the arch input reads as `decode_kv_lens`; charge is never written back
into it. `kv_usage` is hard-tier units over `capacity_units`, and `kv_snapshot`
values are units.

`kv_overhead` picks the byte counts:

| | `vllm` (default) | `none` |
|---|---|---|
| Entry bytes | `padded_bytes_per_entry` where declared | `bytes_per_entry` |
| Per-request state copies | `copies` held; vLLM's max-concurrency estimate adds one in align mode (prefix caching on, an engine block, a reusable state), which a running request does not hold | 1 |
| Per-token rounding | whole `EngineOverhead.block_tokens` blocks | 1 token |
| Budget | minus `fixed_device_bytes` | whole |
| Window, running / admission | `W - 1 + step` / `W - 1 + max_in_flight` | `W` / `W` |
| Default `prefix_resume_points` (§3.2) | `prompt_end` | `response_end` |
| Default `prefill_chunk_alignment` (§4) | `checkpoint` | `plain` |

`vllm` is what vLLM allocates, for alignment and prediction. `none` is what the
model must persist: an upper bound on capacity and prefix reuse whose gap to
`vllm` is the engine's overhead. `max_in_flight` is `kv_max_in_flight_tokens`,
else two steps of `max_batch_tokens` (vLLM async scheduling), else the whole
prompt.

The options are one flattened `KvAccountingSpec` in every KV worker selector:
`kv_overhead`, `prefix_resume_points`, `prefix_resume_interval`, and
`kv_max_in_flight_tokens`. `run_meta.json` records each pool's
`capacity_units`, `bytes_per_unit`, and `kv_overhead` under `kv_pools`, so units
convert back to bytes.

### 3.2 Session-prefix ownership, resume positions, and shared capacity

`SessionInput::Session` is one closed immutable declaration containing the
session id, that session's first trace-declared arrival, and the reusable-prefix
requirement. The declared prefix is not a cache-hit fact.

`SessionInput::PinnedPrefix` is the exception: a standalone request whose trace
declares `prefix_tokens` already resident on arrival (the independent format's
optional `prefix_len` column). Every prefix-capable KV resolves it as
`resident = declared = prefix_tokens` on whichever partition admission picks,
regardless of that partition's cache or `prefix_cache_mode`. It creates no
placement affinity, emits no `prefix_cache_event`, and is never retained: the
reservation of `fresh + prefix_tokens` (+ output) covers the prefix KV and
completion releases it with the request.

For a fresh suffix `fresh`, declared prefix `declared`, and physically retained
hit `resident`, `KvCacheStore` resolves:

```text
prefill_tokens_to_compute = fresh + (declared - resident)
post_prefill_context_tokens = fresh + declared
```

The names intentionally separate declarations, runtime facts, and policy keys:

| Name | Owner | Exact meaning |
|---|---|---|
| `SessionInput` | request definition | `Standalone`; `PinnedPrefix`, a standalone request with a trace-declared resident prefix; or one closed session declaration containing id, first trace arrival, and declared reusable-prefix length |
| `ResolvedPrefillContext` | `KvCacheStore` | One request's partition-specific resident, compute, and post-prefill context facts |
| `resident_prefix_tokens` | resolved prefill context | Declared prefix tokens physically found on the chosen partition |
| `prefill_tokens_to_compute` | resolved prefill context | Fresh prompt plus the declared-prefix miss |
| `post_prefill_context_tokens` | resolved prefill context | Full logical context after prefill: fresh prompt plus declared prefix |
| `RequestTelemetry.prefix_cache_hit_tokens` | request telemetry | Admission's immutable copy of `resident_prefix_tokens`; `None` means admission never resolved, while `Some(0)` is a real miss |
| `request_slo.fresh_prompt_tokens` | per-request log | Immutable fresh suffix, kept separate from runtime compute work for request-level conservation |
| `request_slo.declared_prefix_tokens` | per-request log | The immutable request declaration copied for direct request-level analysis |
| `request_slo.prefix_cache_hit_tokens` | per-request log | The nullable runtime observation copied from request telemetry; miss tokens and hit rate are derived from the two logged counts |
| `prefix_cache_event` | per-worker KV log | Exact ordered `activate`/`evict`/`retain` transitions returned by the authoritative prefix cache ledger |
| `PrefixCacheReturnMetadata` | prefix cache | Replacement-policy history carried while a destructively consumed entry is active; not a lock or capacity lease |
| `conversation_start_time` | admission candidate | Session's first trace-declared arrival, falling back to standalone request's actual arrival |
| `SessionStartOrder` | pending policy | Oldest value of the preceding key first, then enqueue sequence |

`resident` is the largest **resume position** of the session's entry at or below
`declared`, or 0. Per-token KV can resume at any length, but a sliding window or
a recurrent state only where the engine kept it, so an entry records the
positions its request left behind (`ResumePositions`). A request that finished
at `context` tokens after a `prompt`-token prompt (fresh plus declared) keeps:

| `prefix_resume_points` | Positions | Matches |
|---|---|---|
| `prompt_end` | the prompt end; `prompt - 1` under `vllm`, which recomputes a resend's last prompt token | vLLM `prefix_cache_retention_interval = 0` |
| `response_end` | `context` | a next turn that keeps the previous answer in its history |
| `prompt_and_response_end` | both | both reuse patterns |
| `every_block` | every engine block up to `context` | vLLM retention `None` |

Under `vllm` positions are floored to the engine block; `prefix_resume_interval` adds
every multiple of that many tokens (a positive multiple of the block). A layout
whose reusable parts are all per-token ignores the option and resumes at any
block. A part with `prefix_reusable: false` adds no constraint: the hit stands
and that part recomputes its window. The entry keeps per-token KV only up to its
last position, since nothing past it can be resumed, and is charged
`KvAccounting::entry_charge`; when the slack cannot hold it all, the latest
positions are dropped first.

Under `vllm`, a multi-turn session on a hybrid model therefore resumes at the
previous prompt and recomputes the previous answer plus the new user text.
With turn 1 at prompt 8000 plus 500 output tokens and turn 2 declaring 8500
shared tokens, the hit is 8500 for a full-attention layout, 7999 for an SWA
hybrid, 7392 for a GDN hybrid on 1056-token blocks (8448 with `every_block`),
and 8500 for any layout under `none` (`resume_points_follow_the_policy`).

A running request already keeps the window tails and states at the positions
it has passed (`checkpoint_units`). These **live checkpoints** share the soft
tier with retained prefixes: evictable, outside `fits` and `kv_usage`, and
first in line for slack because they are about to become an entry. They are
never proactively shed.

Admission gates `prefill_tokens_to_compute` and reserves the full
`post_prefill_context_tokens`. Execution receives the resident and compute
fields from `ResolvedPrefillContext`; no runtime hit/miss or resident count is
written into request progress. Admission copies the resolved hit count once into
`RequestTelemetry`, and L7 persists it with the declaration in `request_slo`.
A disabled or cold cache therefore records `Some(0)` and recomputes the whole
declared prefix instead of treating the declaration as an automatic hit. A
request that never reaches admission remains `None`.

For every request that reaches decode, the request log must close these
independent conservation equations:

```text
hit + computed = fresh + declared
actual_causal_prefill = computed * hit + computed * (computed + 1) / 2
actual_causal_prefill + hit * (hit + 1) / 2
    = (fresh + declared) * (fresh + declared + 1) / 2
```

For a worker with multiple attention partitions, admission asks `PrefixKv` for
the partition with the largest retained match before consulting its fallback
load balancer. Equal matches choose the lower partition deterministically. The
retained owner is a hard affinity: if that partition cannot currently admit the
request, the selected head waits rather than recomputing another copy elsewhere.
Only a cold or evicted session reaches the fallback balancer (round-robin, or
vLLM's least-loaded rule under the chunked worker's `dp_placement`). Because an active
request destructively owns the consumed cache entry, active KV is not offered as a
shareable match.

The retained prefix cache is an evictable tier *inside* the partition's
configured attention memory, never an additional pool. By default it may use
all attention KV slack left by higher-priority ownership. The physical invariant
is:

```text
max(active resident + promised + held,
    projected active peak + promised + held)
+ live checkpoints + retained prefix
<= total attention KV capacity
```

`fits` may ignore retained entries only because they are evictable; `reserve`
immediately shrinks them to the remaining physical slack. A hit destructively
moves one session entry into the active request, so the current implementation
does not model inter-request prefix sharing or ref-counted pages. Completion
returns the request's context, cut at its last resume position, to that
partition's session cache.
For PD, source KV remains `held` until the decode pull acknowledgement; only then
does it become evictable retained prefix, preventing held and cached ownership
from being counted simultaneously.

Barebone, HP unified, PD prefill, and AFD-attention selectors expose three
orthogonal knobs: `prefix_cache_mode` (`opportunistic` by default or explicit
`disabled` baseline), `prefix_cache_policy`, and the optional
`prefix_cache_max_gpu_memory_gb`. An absent maximum means “use any dynamically
available slack”; a present maximum only caps retained occupancy and must fit
inside `attn_gpu_memory_gb`. Active, promised, and PD-held KV can always evict
retained entries regardless of that maximum. PD decode does not own this tier;
it consumes the exact full-context token count carried by the prefill handoff.
Host tiers and content-level/radix sharing remain separate future capabilities.

KV observation preserves this single-pool model. `kv_snapshot` values are KV
units. `active_kv` is the total committed attention occupancy, including
retained entries and live checkpoints (clamped to the slack), and
`retained_prefix_kv` is its prefix-cache component. Throttling captures both from
the same submit that set the active-window peak; it does not take an independent
prefix maximum. Thus a logged row can be decomposed as
`non_prefix_active_kv = active_kv - retained_prefix_kv`.

The complementary `prefix_cache_event` stream is mutation-complete rather than
sampled. Each prefix-capable KV worker writes a strictly increasing `sequence`,
the triggering request and affected session, an operation/reason pair, and the
entry/cache token counts immediately before and after the mutation. An
`activate` also records `full_hit_tokens`, the declared prefix capped at the
context the entry keeps: its gap to `hit_tokens` is what resume positions cost
the hit. Admission emits `activate` for both a resolved hit and miss. Normal completion emits
`retain`; PD prefill waits for the decode pull acknowledgement before emitting
its `handoff-complete` retention. Evictions identify active-KV pressure,
replacement-policy selection, retention-capacity shrink, or same-session
replacement. The replay invariant is:

```text
cache_used_after
  = cache_used_before - entry_tokens_before + entry_tokens_after
```

Per-partition consecutive rows also chain the previous `cache_used_after` into
the next `cache_used_before`. These rows come directly from `PrefixCache`
mutation receipts. A typed `PrefixCacheEventKind` restricts operation/reason
pairs before the logger converts them to parquet strings. Neither the logger nor
an analyzer owns a shadow cache, and decode-token growth remains in the normal
KV ledger and `kv_snapshot` rather than inflating this sparse operation stream.

## 4. Admission lifecycle × selection

Admission has two independent responsibilities:

- **Lifecycle:** when a request may move from pending to reserved, resident,
  handed off, or complete.
- **Selection:** which not-yet-started request is considered next.

Pending membership belongs entirely to `PendingOrderPolicy`. A lifecycle owns no
shadow pending queue:

```rust
trait PendingOrderPolicy {
    fn push(&mut self, candidate: AdmissionCandidate);
    fn peek(&self) -> Option<&AdmissionCandidate>;
    fn pop(&mut self) -> Option<AdmissionCandidate>;
    fn remove(&mut self, request: RequestId) -> Option<AdmissionCandidate>;
    // membership/count/accounting observations
}
```

`AdmissionCandidate` freezes selection facts at enqueue. The concrete
`conversation_start_time` key is the session's first `arrival_time` declared in
the trace, or the request's own release for a standalone request. Replay rate,
closed-loop backpressure, and tool wait do not rewrite a session's logical age.
`SessionStartOrder` maintains this oldest-first heap and uses a monotonic enqueue
sequence for deterministic ties. Production fresh-request builders select it.
`FifoOrder` and `ShortestJobFirst` remain explicit composition seams; their
semantics are not silently changed by the production selection.

The production lifecycle families are:

- `LocalPrefillDecodeAdmission<P>` — local prefill, decode, completion.
- `PrefillHandoffAdmission<P>` — prefill, source-KV hold, handoff and pull ack.
- `FreshRequestSlotAdmission<P>` — AFD attention's two-level gate: accept a
  fresh request into `P`, then reserve fitting heads for slot placement.

The last family implements the separate `SlotPipelineAdmission<K>` trait. It
does not expose `form_batch` or `complete_iteration`; the slot shell owns
layer-wise cadence, while paired FFN work owns terminal bookkeeping.

Not every queue in a worker is a selection policy. A queue is a policy only when
its job is choosing which fresh request starts next. Landed PD requests, active
slot work, and FFN tasks are cadence state owned by their shells.

Chunked prefill follows the same distinction: the policy owns fresh requests
that have not started; a partition-local lifecycle owns the started prompts that
still have chunks to run, in start order. The complete request KV footprint is
reserved once. A partition may contain many resident prefills over time, but it
never rotates partial chunks through the selection queue. Skipping a started
prompt preserves its order and identity. Without a chunk-end quantum a partial
chunk spends the rest of the budget, so at most one prompt is partial per
partition. A hybrid engine that can checkpoint recurrent state only on block
boundaries (vLLM's Mamba `align` cache mode) ends every non-final chunk on one;
the lifecycle takes that quantum as configuration, and the budget a clipped chunk
leaves may start further prompts, so several can be partial at once. The recipe
derives the quantum with `prefill_chunk_end_quantum`: the layout's engine block,
when the layout keeps a resumable per-request state, prefix caching is on, and
`prefill_chunk_alignment` is `checkpoint` (unset follows `kv_overhead`: `vllm`
aligns, `none` does not). The speculative recipe uses the same derivation; its
arch also states whether the drafter prunes the last matching prefix block
(vLLM's `use_eagle_block_drop`), which moves the prompt's last checkpoint one
block earlier.

Admission never computes KV charges itself. It asks the store for a footprint
(§3.1) and calls `fits`/`reserve`; a retracting lifecycle likewise asks the
store whether the next decode step's growth fits (`prepare_next_decode`). Only
the hard tier enters these gates.

The whole-iteration shell retains an explicit per-iteration batch plan between
formation, input lowering, and completion. Under `mix`, resident decode and
prefill share the chunk token budget. Under `separate-prefill-priority`, a
runnable prefill suppresses decode only for that iteration: decode membership
and KV remain resident, but execution omits it and completion neither emits a
token nor advances its KV. This models a batch boundary, not a capacity policy;
optimistic future-token estimates and decode retraction require their own KV and
lifecycle contracts rather than a flag in resident partition state.

## 5. Execution axis

Execution owns the model instance, reusable input buffers, input lowering, and
cost buffers. The production sibling traits are intentionally per family:

- `IterModelExecution<K>` — builds its associated input (`UnifiedArchInput` or
  `SpeculativeArchInput`) and evaluates a whole iteration.
- `AttentionLayerExecution` — builds `AttnArchInput` for one slot and evaluates
  one attention layer.
- `FfnTaskExecution` — builds `FfnArchInput` and evaluates FFN
  Bootstrap/Bridge/Terminal sections.

Their concrete adapters are `UnifiedIterExecution`, `SpeculativeIterExecution`,
`AttentionLayerExecutionAdapter`, and `FfnSectionExecutionAdapter`.

`UnifiedIterExecution` always builds one group per KV partition. Multi-partition
workers also retain the exact per-partition token vector for EP collectives;
the execution adapter derives it from the same groups. This is an
input-lowering fact, not a placement or scheduling policy.

The shell treats `E::Input` as opaque. Transfer submission stays in the shell
because its timing and overlap are cadence facts, not model math.

## 6. Production cadence families

### 6.1 Whole iteration

`workers/iter/IterBatchWorker` runs:

```text
form_batch → build/evaluate iteration → complete_iteration → repeat
```

Barebone, head-parallel unified, and PD prefill reuse this cadence with different
recipes.

### 6.2 Pull plus decode

`workers/pd_decode/PullDecodeWorker` coordinates two timelines:

- one serialized KV pull with a bounded landed/in-transit backlog;
- one whole-iteration decode FSM.

A request becomes resident only after prompt KV lands. Pull completion
acknowledges the exact prefill worker holding the source capacity.

### 6.3 Layer-slot attention

`workers/afd_attention/SlotAttentionWorker` combines fresh-request admission
with a private three-slot pipeline. Each slot walks:

```text
Wait → WaitComplete → Pull → PullComplete → Compute → AwaitFlush
```

At most one slot pulls and one computes. L6's all-worker layer barrier releases
`AwaitFlush`, so empty attention shards remain in lockstep.

### 6.4 Buffered FFN

`workers/afd_ffn/BufferedFfnWorker` has no KV or request-admission component. L6
delivers complete `FfnTask`s, and the worker overlaps one incoming gather with
one current section compute:

```text
incoming → pulling_task → computing_task → SectionReady / IterComplete
```

Terminal owns token emission and request completion while preserving the sticky
attention worker as the request's recorded location.

### 6.5 Pipeline stages

`workers/pipeline/` has two shells. `PipelineHeadWorker` is stage 0: it owns
admission and the pipeline's KV, runs stage 0's compute, and keeps at most
`depth` microbatches in flight. `PipelineStageWorker` is every later stage: no KV
or admission, FIFO, one activation pull overlapped with one compute.

The head's lifecycle is a separate admission surface, `MicrobatchAdmission`,
because several microbatches are in flight at once.
`PipelinedChunkedPrefillAdmission` commits a chunk's prefill progress at
formation and emits tokens when their microbatch leaves the last stage, so one
prompt can be sliced across consecutive in-flight microbatches. A decode step
needs the previous token, so a running request has at most one microbatch in
flight (vLLM V1: no new tokens to schedule until the output returns). Each
microbatch takes the ready decodes, then started and fresh prompts, under one
token budget; the selected decode subset travels in the shell's `IterBatchPlan`
to input lowering, and only that subset advances in KV at exit. Decode
selection is greedy by default, as in vLLM, so requests that become ready
together share one microbatch; `balance_decode_microbatches` caps each
microbatch at `ceil(resident decodes / depth)` so they split across the depth. Completion is
owned by the head, at the exact exit time the last stage reports.

## 7. Current compositions

| Worker selector | KV | Admission | Execution | Shell |
|---|---|---|---|---|
| `barebone` | `KvCacheStore` | `LocalPrefillDecodeAdmission<SessionStartOrder>` | `UnifiedIterExecution` | `IterBatchWorker` |
| `hp_unified` | `KvCacheStore`, N partitions | `LocalPrefillDecodeAdmission<SessionStartOrder>` with retained-prefix affinity, then round-robin on misses | `UnifiedIterExecution` | `IterBatchWorker` |
| `chunked_prefill` | `KvCacheStore`, N partitions | `ChunkedPrefillAdmission<PendingOrder, SingleTokenDecodeCompletion>` | `UnifiedIterExecution` | `IterBatchWorker` |
| `speculative` | `KvCacheStore`, N partitions | `ChunkedPrefillAdmission<PendingOrder, SpeculativeDecodeCompletion>` | `SpeculativeIterExecution` | `IterBatchWorker` |
| `pd_prefill` | `KvCacheStore` with held ledger | `PrefillHandoffAdmission<SessionStartOrder>` | `UnifiedIterExecution` | `IterBatchWorker` |
| `pd_decode` | `KvCacheStore`, less the reserved pull budget | thin landed-request ingress | `UnifiedIterExecution` | `PullDecodeWorker` |
| `disagg_attn` | `KvCacheStore` | `FreshRequestSlotAdmission<SessionStartOrder>` | `AttentionLayerExecutionAdapter` | `SlotAttentionWorker` |
| `disagg_ffn` | none | none | `FfnSectionExecutionAdapter` | `BufferedFfnWorker` |
| `pipeline_chunked_prefill` (stage 0) | `KvCacheStore`, one partition, sized by the most constrained stage's layout | `PipelinedChunkedPrefillAdmission<PendingOrder>` | `UnifiedIterExecution` | `PipelineHeadWorker` |
| `pipeline_chunked_prefill` (later stages) | none | none | `UnifiedIterExecution` | `PipelineStageWorker` |

Hybrid archs (sliding-window, recurrent, or compressed state) use these same
selectors and recipes; their `KvCacheLayout` changes only the charges (§3.1),
and the chunked recipes take the chunk-end quantum from it (§4).

Aliases such as `BareboneWorker<M>` and `DisaggAttnWorker<M>` name concrete
generic compositions; they are not wrapper runtimes.

`DecodeCompletion` owns the advancement rule within chunked-prefill admission.
Speculative completion reads scalar or per-position conditional acceptance from
the shared request contract, samples before advancing KV, and advances each
accepted-length subset once. Execution submits the matching verify width; the
shell, pending membership and KV ledgers are reused. A request at the model
context limit verifies only the rows that keep its sampled position inside it
(vLLM's scheduler clip), and both execution and completion read that clipped
width from the same rule.

## 8. Construction and file boundaries

Every production recipe lives in one `workers/<family>/build_*_worker.rs` file.
The recipe must visibly choose its KV, admission policy/lifecycle, execution
adapter, and shell.

Repeated mechanical setup may live in a narrowly named essentials helper:
allocation, capacity derivation/registration, sampler creation, cost buffers, and
shared context. An essentials helper must not choose semantic composition. Every
KV-owning recipe resolves its charges with `resolve_kv_accounting` (layout and
options to `KvAccounting`) in `workers/iter_build_essentials.rs`, builds a
prefix-capable store with `kv_cache_store`, and takes its chunk-end quantum from
`prefill_chunk_end_quantum`. PD decode owns no prefix tier
(`KvCacheStore::without_prefix_cache`) and sets its pull budget aside with
`KvAccounting::reserving`.

Deployments and pool controllers call recipes only:

- unified → `build_barebone_worker` / `build_hp_worker` /
  `build_chunked_prefill_worker` / `build_speculative_worker`
- PD → `build_pd_prefill_worker` / `build_pd_decode_worker`
- AFD attention → `build_afd_attention_worker`
- AFD FFN → `build_afd_ffn_worker`
- PP → `build_pipeline_head_worker` / `build_pipeline_stage_worker`

Message/event enums, pool policy, flow barriers, and cross-worker transfer
protocols remain L6 contracts.

## 9. Compatibility and extension rules

Compatibility is capability-based. A combination is excluded only by a semantic
contradiction; “not implemented”, “no preset”, “expensive”, or “the current
worker has another name” are not design-level incompatibilities.

Hard contradictions include:

- a pure FFN shard cannot own decoder KV or fresh-request admission;
- an encoder-only family cannot use the autoregressive decoder-KV lifecycle;
- a no-KV worker cannot expose reserve, handoff, pull, or prefix-KV behavior;
- standard one-token generation cannot silently use draft/verify logits
  semantics.

A missing capability should fail where the concrete recipe is assembled through
trait bounds. It should not be patched with role enums, optional callbacks, or
runtime `match` branches inside shared axes.

SLO/priority changes selection policy, not lifecycle. Prefix reuse is the
`PrefixKv` refinement of the existing KV owner and matching admission/execution
lifecycle; it does not create another KV copy. A future replacement policy that
changes content identity, host tiers, or page sharing must extend that owner
rather than place runtime residency in the request definition.

A new kind of cached state is a new `KvCachePart` in the arch's layout, and a
new growth rule is a `KvGrowth` variant charged in `KvAccounting`; neither is a
new KV store. Another engine's allocator (SGLang's separate SWA and mamba pools,
its decode reservation) would be a new `KvOverhead` value, and only a second
physical pool would need a second ledger.

Add a new shell only when cadence, overlap, synchronization protocol, or
completion ownership truly changes. Otherwise add the smallest new leaf
component or thin adapter and reuse the existing recipe shape.

An unknown variant fits the abstraction when it can be added with:

1. one new leaf component or necessary thin adapter;
2. one declarative build recipe/registration;
3. focused contract and behavior tests;
4. no copied tick loop, pending ledger, KV ledger, or ArchInput lowering.

If those conditions fail, first identify which ownership boundary is wrong;
do not grow a universal “supports everything” trait.

## 10. Preservation and validation

A composition refactor is correct only when it preserves externally observable
simulation semantics:

- request placement and stable selection order;
- admission gates, KV residency, held/reserved accounting, and release timing;
- modeled event ordering, transfer overlap, and completion ownership;
- KV sampling and cost-log row/manifest structure;
- modeled throughput and deterministic summary fields for the same complete
  preset, model config, workload, and profiling database.

Wall-clock runtime and `realtime_x` are host-performance observations and may
vary; they are not modeled-output equivalence fields.

KV accounting has its own checks. A layout of one per-token part counts plain
tokens: capacity is exactly the partition budget over its per-token bytes, so a
full-attention arch is a regression baseline for any store change. A layout or
`kv_overhead` change that moves capacity, prefix hits, or chunking changes
predictions on purpose; pin it with a capacity test against vLLM's logged
concurrency (L4.md, KV cache layout) and re-record goldens only after the change
is reviewed.

Validation should include scoped unit/contract tests, `cargo check` for the
simulator library, and representative unified, PD, HP/MoE, and AFD runs. When
comparing branches, use the same resolved model JSON and the same filled profile
database; otherwise a configuration/cache difference can masquerade as a worker
semantic difference.

## 11. Layer invariants

- L5 owns mutable serving state; L4 and below remain pure cost queries.
- KV, admission, and execution have one owner each; the shell owns cadence.
- Selection policy is the sole owner of not-yet-started pending membership.
- Request-to-KV-partition placement is sticky for the request's KV lifetime.
- Retained session prefixes are worker-local sticky placement facts; fallback
  load balancing runs only when no partition retains the prefix.
- Active/promised/held KV and retained prefix KV share one physical attention
  capacity; retained prefix and live checkpoints are the evictable soft tier of
  that same space and never gate admission.
- `KvCacheStore` is the only KV store. It counts KV units from `KvAccounting` and
  never sees layout parts; the arch's layout is the only source of KV bytes.
- `current_kv` is context tokens for the cost model; KV charge is units and is
  never written back into it.
- Model input construction lives on the execution/model side, never in KV or
  admission.
- L4-reported cost time advances the L5 compute clock.
- L6 receives pushed typed events; L5 has no drainable event outbox.
