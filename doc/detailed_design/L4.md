# L4 — Model arch

A **model_arch** wires a full model, or one model section for a disaggregated
worker family, from L3 worklets. It forwards resolved model and parallel
configuration into those worklets, owns the parallel layout, and compiles each
reused CostTree once. L4 is L5's sole view of model math and topology.

## Role and boundary

- **Sees:** worklets, model dimensions, parallel layout, routing distribution,
  and profiling/timing bridges.
- **Does not see:** request lifecycle, KV residency, admission queues, worker
  cadence, transfers, or the simulation clock.

L5 supplies an input value and caller-owned reusable buffers. L4 evaluates the
matching compiled cost structure and returns `LeafMetrics`; `.m.time_ms` is the
modeled compute duration used by the worker.

## L4 ↔ L5 contracts

The contract is split by execution family rather than widened with optional
methods.

### Iter-wise unified

`IterwiseUnifiedModel` costs one complete embedding → layers → lm-head
iteration:

| Method | Role |
|---|---|
| `eval_iter(batch, slots, scratch)` | evaluate the compiled tree, fill per-leaf metrics, and return the aggregate |
| `eval_iter_with_inputs(...)` | the same path plus typed `SlotInput` capture for `cost_log` |
| `cost_log_manifest()` | expose the flattened slots/nodes needed to reproduce the aggregate |
| `kv_cache_layout()` | one request's persistent KV state, part by part, summed over one KV partition's ranks (see [KV cache layout](#kv-cache-layout)) |
| `gpus_per_replica()` | physical GPU extent of one model replica |
| `num_attn_dp_groups()` | independent attention-DP groups; one L5 KV partition per group |
| `num_attn_shards()` | GPUs participating in one attention shard |

`UnifiedArchInput` contains one `ArchGroupInput` per attention-DP group plus
`tokens_per_source_rank` for the FFN routing view. Each group carries batch token
counts, prefill chunk pairs, decode KV lengths, and cumulative KV occupancy.

`SpeculativeUnifiedModel` and `AttnLayerwiseModel` carry the same required
`kv_cache_layout()`.

### KV cache layout

A model's persistent attention state is not one per-token number: global
attention grows with every token, a sliding window keeps only its last `W`
tokens, a compressed cache keeps one entry per few tokens, and a recurrent layer
keeps one state per request. `kv_cache_layout()` returns a `KvCacheLayout`
(`arch/kv_layout.rs`): a list of `KvCachePart`s and one `EngineOverhead`.

Each part has a `name`, a `growth`, `bytes_per_entry`, `prefix_reusable`, and an
`overhead`:

| `KvGrowth` | One request holds | Examples |
|---|---|---|
| `PerToken { tokens_per_entry }` | one entry per `tokens_per_entry` context tokens, for its whole life | GQA/MLA KV (`1`); GLM-5.3-Flash kpool indexer; DeepSeek-V4 C4/C128 caches |
| `SlidingWindow { window_tokens }` | one entry per token, for the last `window_tokens` tokens | SWA layers; Inkling short conv (`W = 4`); DeepSeek-V4 compressor state |
| `PerRequest` | one entry, whatever its length | GDN/KDA conv + SSM state; GLM-5.3-Flash kpool tail; DeepSeek-V4.1 compressor ring |

Bytes are **total**, not per rank: summed over the part's layers and over every
rank of one KV partition (one attention TP group). L5 multiplies the per-GPU
attention budget by `num_attn_shards()` to match. A GQA layer whose TP exceeds
its KV head count stores a replicated head on each rank;
`gqa_kv_bytes_per_token` counts `max(num_kv_heads, attn_tp)` heads.

`bytes_per_entry` is what the model must store. What the serving engine
allocates on top is declared separately, so L5 can charge it or not
(`kv_overhead`, L5 §3.1):

- `PartOverhead { padded_bytes_per_entry, copies }`: a larger allocated entry
  (Inkling's conv head padded to a power of two, a mamba state padded to the
  attention page, DeepSeek-V4/V4.1 packed-group pages) and extra state copies
  such as vLLM's speculative blocks. vLLM align mode's previous-step state copy
  is not declared here; L5 adds it when prefix caching is on.
- `EngineOverhead { block_tokens, fixed_device_bytes }`: an engine block whose
  rounding matters (vLLM's hybrid allocator scales it to fit a mamba page,
  1056 to 2304 tokens; DeepSeek-V4/V4.1 pack groups into 256/128-token blocks),
  and bytes taken from the budget before the pool is sized (null block,
  persistent buffers). Ordinary 16-token block rounding, layer grouping, and
  page unification are not modeled.

`prefix_reusable: false` marks state a later request cannot resume from: a
window the engine always replays (DeepSeek-V4.1's bounded-replay SWA) or a
buffer it never caches (GLM-5.3-Flash kpool tail). A PP arch exposes the layout
of its most constrained stage (the most per-token bytes) as
`pipeline_kv_cache_layout()`; every stage holds the same requests.

An arch with a vLLM capture pins its layout with a unit test that resolves it
at the logged KV budget and compares `KvAccounting::concurrency_at` with vLLM's
"Maximum concurrency" line (`kv_cache_layout_reproduces_vllms_packed_groups` in
`deepseek_v4_vllm.rs` / `deepseek_v41_vllm.rs`, within 0.5%).

### Layer-wise AFD

AFD uses sibling contracts:

- `AttnLayerwiseModel` consumes `AttnArchInput`, evaluates one attention layer,
  and reports its outgoing attention→FFN wire bytes per token.
- `FfnLayerwiseModel` consumes `FfnArchInput`, evaluates
  Bootstrap/Bridge/Terminal sections, and reports outgoing FFN→attention wire
  bytes per token.

Both expose section-aware cost manifests and the same caller-owned
`slots`/`scratch` protocol as the iter-wise contract. Transfer sizes are reported
by the sending model side; L5/L6 do not rederive tensor layouts.

The FFN Bridge split bills post-attention work for layer `L` together with the
fused pre-attention work for `L+1`. Bootstrap bills the first pre-attention
section and Terminal bills the final post-attention section, so every logical
model operation is counted exactly once.

## Build shape

Every concrete arch follows:

```text
build_configs(model, parallel, ...) → raw worklet/op configs
                 │
          resolve_configs
                 ▼
          resolved per-rank shapes
                 │
               build
                 ▼
       model with compiled CostTree section(s)
```

`build` instantiates worklets/ops through the profiling bridge, compiles each
stable cost structure, and caches its flattened nodes and slot count. A hot-path
evaluation therefore performs leaf evaluation plus aggregation only: no
per-tick tree compilation, name construction, or scratch allocation.

For homogeneous layers the iter-wise tree uses `Scale { n: num_layers }` over
one compiled layer. Layer-wise AFD compiles its distinct attention and FFN
sections once and receives `layer_idx` only where section behavior changes.

## Model dimensions and parallelism

- `ModelCfg` holds dense-decoder dimensions loaded from Hugging Face-style model
  JSON.
- `MoeModelCfg` holds the MoE extension, including expert counts and routing
  dimensions.
- `ParallelCfg` and family-specific parallel structs own resolved TP/EP/HP
  layout and `gpu_name`.
- The arch is the source of truth for `gpus_per_replica` and attention group
  counts. L5/L6 read these values; they do not reconstruct the topology.

Layer truncation (`num_layers` / `sim_num_layers`) is applied before
`build_configs`, so the compiled structure and reported model metadata agree.

## Selectors and current implementations

Selectors are serde-tagged, provider-first enums. A tag exposes only the
parameters consumed by that arch.

- `IterArchSel`:
  - `qwen36_local`
  - `llama3_dense`
  - `llama3_dense_tp`
  - `llama3_dp_attn_tp_ffn`
  - `qwen3_moe_dp_attn_ep_ffn`
  - `qwen3_moe_fp8_dp_attn_ep_ffn`
  - `qwen3_vllm_moe_dp_attn_ep_ffn`
  - `deepseek_v4_vllm`
  - `deepseek_v4_vllm_serial_streams`
  - `glm52_vllm_dsa_moe`
  - `glm52_vllm_nvfp4_dsa_moe`
  - `glm52_vllm_nvfp4_dsa_moe_speculative`
  - `glm52_vllm_nvfp4_pp_dsa_moe`
  - `glm52_vllm_nvfp4_dp_attn_dsa_moe`
  - `glm53_vllm_nvfp4_dsa_moe_dflash2`
  - `glm52_sglang_nvfp4_tp_dsa_moe`
- `AttnArchSel`:
  - `qwen3_attn_tp` is wired for AFD
- `FfnArchSel`:
  - `qwen3_ffn_moe` is wired for AFD
  - `qwen3_fp8_ffn_moe` is wired for AFD

Provider-specific tags describe measured execution graphs. A generic graph is
retained only when it covers a parallel layout that the aligned provider does
not. See `doc/architecture_compatibility.md` for the current coverage matrix.

`ModelSpec` is flattened into every selector variant and carries
`model_config`, layer controls, and `fp8`. The launcher-generated schema is the
authoritative config surface.

The wired deployment pairings are:

- unified: Llama3 dense/TP with `barebone`; Llama3 DP-attention, Qwen3 MoE, and
  GLM-5.2 DSA/MoE with `hp_unified`;
- PD: the supported Llama3 prefill/decode pairs;
- AFD: `qwen3_attn_tp` with `qwen3_ffn_moe` for BF16/native, or with
  `qwen3_fp8_ffn_moe` for native FP8. The deployment validates that both pool
  model specs select the same precision.

## Layer invariants

- L4 is a pure cost query after construction.
- Stable CostTrees are compiled once and evaluated through caller-owned buffers.
- The arch owns model topology, parallel layout, and transfer payload
  definitions.
- L5 owns mutable lifecycle and converts L4 model facts into worker capacity only
  during construction.
- The arch describes what its KV state is (`KvCacheLayout`); how an engine
  charges, admits, and retains it is L5's.
- A new execution shape gets a sibling typed input/trait rather than optional
  fields on an unrelated contract.
- A framework-alignment recipe and a precision-specific graph are separate L4
  providers. Native BF16 Qwen, native FP8 Qwen, and vLLM-aligned FP8 Qwen do
  not share a recipe enum or a branch-bearing graph builder; only their lower
  L1/L2 mechanisms may be reused.
